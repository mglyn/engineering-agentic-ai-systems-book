# Ch23 会话、事件与状态机

## 23.1 同样的一行聊天记录

报销助手收到了金额 250 的申请。用户的屏幕停在“请求已收到”。他合上电脑，再次打开时，界面还显示这六个字。现在点“继续”，系统应该做什么？

把这个教学案例分别停在两个位置。第一次让连接在工具收到建单请求前断开；第二次让工具提交成功，回执却赶不上连接断开。用户能看见的最后一句话完全相同。第一种情况下还没有工单，第二种情况下已经有了一张。即使模型能逐字背出整段对话，它也无法单凭对话文本判断发生了哪一种情况。恢复所需的信息留在业务系统里。

写这两条路径时，先把客户端发出的**命令**和服务端持久记录的**事件**拆开。“给这笔申请建单”带着执行意图，重复发送可能再次触发工作。“操作已登记”“工单已创建”描述可以核对的事实。重连要先读事实。若仍需执行命令，执行器再查原操作的身份、载荷和权限。[第 36 章](../part9/ch36_reference_implementation.md)在客户端库保存意图，在另一个服务库保存工单和操作 ID；两库独立提交，正好能复现这个时间差。本章新增的观察点在读端。读者将亲手比较三种动作：重建界面、用同一个键重试建单、换一个键重试建单。

## 23.2 一条会话的寿命

一次 HTTP 连接可以在几秒内消失，一笔申请却可能在等人审批后继续。让连接关闭自动取消申请，会把用户换网络解释成撤回授权。会话需要能跨连接识别的身份。实验用一条有序日志代表一个会话，用一个轮次提交申请；正式系统还需要在读取日志前验证租户和用户权限。

下面是本章读端使用的状态机。它比工单对象多了暂停和继续两步。实例选用“用户停下来核对申请”作为暂停点，继续以后才确定最终结果。项目里的工单写入状态由第 36 章定义。一个会话可以取消而业务工单已经存在，因此不能从会话终态倒推出数据库里必有或必无一条记录。

**Fig-23-01　会话投影允许的转移。** 图由本章实验状态表整理。每个终态都没有出边，收到新任务时另建会话或依协议开新轮。

```text
empty → created → running ──completed──→ completed
                    │ ↑
                 paused resumed
                    ↓ │
                   paused
running 或 paused ──cancelled──→ cancelled
running 或 paused ──failed─────→ failed
```

状态转移只有在事件连续时才有意义。客户端手上最后一条是 2，忽然收到第 4 条“已继续”，它可能不知道第 3 条是“已暂停”。此时直接接受第 4 条，会把一个合法恢复误判成非法转移。实现先查会话身份和序号，随后才用“当前状态＋事件类型”查后继状态。状态机只回答在这份已知历史上能发生什么。它没有权限替用户补发建单。

**Tab-23-01　一次继续事件的定位信息。** 本例取自归档的 completed 会话，字段格式见[附录 C](../appendix_c_schemas.md)。

| 信息 | 本地样例 | 用途 |
| --- | --- | --- |
| session_id、turn_id | completed、turn-1 | 定位会话和本次输入。样例为了易读使用固定名 |
| event_id、sequence | completed-4、4 | 识别一条事实及其在本会话的位置 |
| kind、schema_version | resumed、1 | 确定转换和解码规则 |
| occurred_ms | 1004 | 教学事件发生时间；排序依据为 sequence |
| operation_id、ticket_id | T-DEMO-01-completed:1:create、空 | 关联已知写入意图；票号等待服务返回 |

这里会话序号连续。第 36 章 SQLite 表中的 sequence 则是整张表的行号，筛出一个租户或一个任务以后可能出现间隔。把那一列直接当作本章的会话游标，会对其他会话正常占用的行号发起补传。对接时可以另编会话序号，也可以选择不透明的服务端游标，并相应修改客户端的缺口判定。

## 23.3 给恢复留一个起点

把五条事件从头读一遍代价很低。运行一天的会话可能积累数千次工具回调，每次打开页面都从第一条算起，恢复时间会随日志增长。快照保存的是“读完第几条后，状态变成了什么”。本章把快照和这条日志放进同一 SQLite 事务，只有提交之后，读端才能采用它作为起点。[SQLite 事务](https://www.sqlite.org/lang_transaction.html) · [SQLite 隔离语义](https://www.sqlite.org/isolation.html)

设读到序号 2 时，快照记录 running。服务端后来又持久化了 paused、resumed、completed 三件事。客户端从快照恢复时，只要对三条事件依次应用同一个纯函数，就能得到最后的状态和票号。函数的输入是旧视图和一条事件，输出是一份新视图。它不读机器时钟，也不持有工具服务连接。相同字节解码成相同事件，得到相同结果。这正是读端可以反复执行的原因。[Fowler 对事件重建和外部更新的讨论](https://martinfowler.com/eaaDev/EventSourcing.html)

**Fig-23-02　从第 2 条快照重连。** 括号内为当前读端游标。即使最后一个事件先到，也只能在已验证的前缀上继续。

```text
客户端(2)       收到 5 ───── 请求 3 以后所有记录 ─── 依次应用 3、4、5 → (5)
事件服务        已持久化 1、2、3、4、5               提供已提交的连续区间
工单服务        工单已经写入                         不参与回放
```

快照的摘要在本地实验中存放于服务端，客户端携带的状态发生变化会导致摘要比对失败，读端便从零开始。若保存摘要的同一方也能篡改日志，自算摘要不能提供真实性保证。跨机器部署还要约定读取期间的上界。本章在写端关闭后重开只读连接，日志已经静止。在线系统可在一致读事务中选定上界 H，只承诺恢复到 H，随后再追赶新产生的记录。否则一边读、一边追加，“恢复完成”没有可重复核对的位置。[LangGraph 对线程和检查点的说明](https://docs.langchain.com/oss/python/langgraph/persistence)

## 23.4 最后一条丢了

收到 5 而没收到 4，很容易发现中间有缺口。若丢的是最后一条，客户端本地看起来完全正常。它会一直显示“运行中”。实验每次重连都向权威日志读取本会话游标之后的记录，即使客户端尚未观察到跳号，这一步也要执行。传输层若能报告最后一个事件 ID，可以省去一些重复发送；应用仍需规定 ID 指向哪份历史和怎样补齐后缀。[HTML 事件流重连协议](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**Tab-23-02　同一重连入口处理的分歧。**

| 观察 | 判定依据 | 后续动作 |
| --- | --- | --- |
| 同一序号再次到达 | 权威记录在规范化后与来件相同 | 忽略已应用的记录 |
| 同一序号的内容或 ID 变了 | 与保存的事件冲突 | 拒绝该来件，从权威日志补齐 |
| 收到较大的序号 | 本地缺少连续前缀 | 保留已确认游标，从这里追赶 |
| 快照内容、会话或游标不可信 | 会话、摘要或范围校验失败 | 放弃本地快照，从日志开头恢复 |
| 老客户端仍用 seq 字段 | 已定义的 v0 迁移只改字段名及版本 | 规范化后再比较；未知版本回到可解码的权威源 |

这份迁移只覆盖一个已知旧格式。服务端日志本身升级到读端不能理解的版本时，停止推进游标并升级读端才有恢复路径。在客户端丢弃未知事件后，悄悄把序号推进一格，会产生一个内容未知却显示“已同步”的视图。给事件带上来源、身份和类型是跨组件传递的起点。本章的数值序号和连续性是本书另外约定的性质。[CloudEvents 项目](https://cloudevents.io/)

## 23.5 三种“继续”的实际结果

在仓库根目录用 Python 3.12 执行：

```shell
python examples/ch23/session_replay.py --output outputs/ch23/replay.json
```

实验使用原创教学输入和第 36 章的工单服务，生成三条完整会话，分别走向完成、取消和失败。只有完成路径写入了一张工单。每条会话都经过创建、开始、暂停、继续和终止，前两次转移保存快照。程序随后关闭两个写连接，通过 SQLite 的只读 URI 重新打开数据库。20 种条件包括三个位置的重复、三个位置的缺失、乱序、空投递、过期或损坏的快照、协议版本与会话身份等。每种条件在三条会话各跑一次。原始报告保留了实际投递、恢复动作、终态、两张业务表的行数和耗时。[SQLite 只读 URI](https://www.sqlite.org/uri.html)

实际运行的 **60/60 次**回放都恢复了预期的序号 5 和对应终态。完成会话仍有 1 张工单和 1 条服务审计记录；另外两条会话仍然都是零。只数工单不足以证明回放没有调用写接口，因为第 36 章的服务能拒绝重复作用。本实验还数审计记录，并让回放程序只持有事件日志的只读连接。它在接口上就无法调用建单方法。

把报告中的 completed 会话拿出来，单看最后两个对照。原命令以**相同操作 ID**重试，服务返回原票号 1，工单数保持 1，审计行数从 1 增至 2。随后让只保留聊天文本的示范客户端采取一种危险但常见的恢复策略：把“继续”当成新的提交，为相同载荷生成**新操作 ID**。服务收到了另一个合法请求，工单数从 1 增至 2，审计行数从 2 增至 3。只有聊天记录的客户端也可以选择停下来查单；实验所揭示的是，聊天文本本身不能替它选择一个安全的重试键。有关重复请求的预期作用，可参照 [HTTP 幂等语义 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

本地报告的 elapsed_us 从开始校验快照到结束补传，用单调时钟实测，不包含网络往返、建单和生成初始日志。一次性运行这 60 个教学输入可以检验恢复逻辑；要估计服务延迟，仍需固定输入规模、引入并发负载并重复采样。[第 27 章](../part7/ch27_benchmarking_capacity.md)给出了分位数的记录方法。

## 23.6 重连验收

当用户重新打开页面时，界面可以先显示“正在核对”，随后展示服务端确认的终态和票号。审批已失效、但原工单已写入时，还需根据当前查询权限决定能展示多少信息。回放解决状态重建，业务查权仍由服务负责。下一章把同一个问题缩短到毫秒级：界面已经进入新轮，上一轮的回调仍然可能到达。[第 24 章](ch24_streaming_interrupts.md)

1. 服务端收到“取消申请”和服务端记录“申请已取消”，哪一个可以直接应用到只读视图？为什么？
2. 只剩 10 毫秒可用于恢复时，应怎样测量并调整快照间隔？
3. 游标没有跳号，界面却一直显示“运行中”。怎样区分任务真的在运行和最后一个事件丢失？
4. 工单数量没有增加，服务审计行数增加一行，这说明读端一定只做了回放吗？
5. 下一轮用户输入已经开始，上一轮的完成事件才到达。哪些信息仍应记入账本，哪些需要在呈现端检查？

**实践题。** 从报告中取 completed 的 missing_middle 和 missing_end 两条记录，标出客户端发现缺口的第一个机会，给出两条恢复后相等的字段和一项独立的业务证据。然后在临时副本中取消最后的权威补传，重跑并定位第一个未闭合的游标。进阶可按每 100 条、每 1000 条存一次快照，测量固定长度日志的恢复耗时，并报告实验机器和样本数。
