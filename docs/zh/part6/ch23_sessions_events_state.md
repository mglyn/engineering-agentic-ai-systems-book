# Ch23 会话、事件与状态机

## 23.1 同样的一行聊天记录

用户在报销助手里提交一笔 250 元的申请，屏幕停在“请求已收到”。他合上电脑，过一会儿再打开，界面上显示的还是这句话。此时如果他点“继续”，光看页面并不知道刚才那张工单到底建没建成。

断线可能发生在工具收到建单请求之前，业务库里尚无工单；也可能发生在建单已经提交、回执尚未传回之时，工单已经落库。两种现场留给用户的最后一行提示完全一样，业务库里的状态却正相反。即便模型能逐字复述整段对话，也无法单凭聊天文本判断当时断在哪一步，恢复必须回到业务系统查证。本章的三路查库对照就从已有工单开始。

处理这两条路径，得先把客户端发出的**命令**和服务端持久记录的**事件**拆开。“给这笔申请建单”表达的是执行意图，重复发送可能再次触发建单；“操作已登记”“工单已创建”记录的则是可以核对的事实。重连时必须先读事件回放状态；如果确认仍需执行命令，再由执行器核对原操作 ID、载荷和权限后发起重试。[第 36 章](../part9/ch36_reference_implementation.md)在客户端库保存写入意图，在独立的服务库保存工单和操作 ID，两库分开提交正好能复现这个时间差。本章把观察点放到读端，并把只读回放、按原操作 ID 重试建单、换新操作 ID 重新提交放在一起对照。

## 23.2 一条会话的寿命

一次 HTTP 连接可以在几秒内消失，一笔申请却可能在等人审批后继续。让连接关闭自动取消申请，会把用户换网络解释成撤回授权。会话需要能跨连接识别的身份。实验用一条有序日志代表一个会话，用一个轮次提交申请；正式系统还需要在读取日志前验证租户和用户权限。

Fig-23-01 是本章读端使用的状态机，比工单对象的生命周期多了暂停和继续两步。实验以“用户停下来核对申请”作为暂停点，状态机里的 resumed 指用户核对完申请后继续推进业务，随后进入终态；它与断线客户端重连以补齐显示是两回事。业务工单自身的写入状态仍由第 36 章定义，两者并不一一对应。比如用户迟迟没收到回执便点了取消，会话已进入取消终态，但工单可能早已提交落库，因此不能根据会话终态断言数据库里一定有或一定没有这张工单。

**Fig-23-01　会话投影允许的转移。** 图由本章实验状态表整理。每个终态都没有出边，收到新任务时另建会话或依协议开新轮。

```text
empty → created → running ──completed──→ completed
                    │ ↑
                 paused resumed
                    ↓ │
                   paused
running 或 paused ──cancelled──→ cancelled
running 或 paused ──failed─────→ failed
```

状态转移只有在事件序号连续时才能成立。如果客户端本地最后一条是序号 2，忽然收到序号 4 的“已继续”，它根本不知道中间漏掉了序号 3 的“已暂停”；这时直接拿当前状态去匹配第 4 条，就会把一次合法恢复误判为非法转移。因此归约代码会先校验会话 ID 和序号是否连续，确认无误后再按“当前状态＋事件类型”查找后继状态。状态机只负责根据已知事件推演当前视图，不负责也没有权限替用户补发建单。

**Tab-23-01　一次继续事件的定位信息。** 本例取自归档的 completed 会话，字段格式见[附录 C](../appendix_c_schemas.md)。

| 信息 | 本地样例 | 用途 |
| --- | --- | --- |
| session_id、turn_id | completed、turn-1 | 定位会话和本次输入。样例为了易读使用固定名 |
| event_id、sequence | completed-4、4 | 识别一条事实及其在本会话的位置 |
| kind、schema_version | resumed、1 | 确定转换和解码规则 |
| occurred_ms | 1004 | 教学事件发生时间；排序依据为 sequence |
| operation_id、ticket_id | T-DEMO-01-completed:1:create、空 | 关联已知写入意图；票号等待服务返回 |

这里会话序号连续。第 36 章 SQLite 表中的 sequence 则是整张表的行号，筛出一个租户或一个任务以后可能出现间隔。把那一列直接当作本章的会话游标，会对其他会话正常占用的行号发起补传。对接时可以另编会话序号，也可以选择不透明的服务端游标，并相应修改客户端的缺口判定。

## 23.3 给恢复留一个起点

把五条事件从头读一遍代价很低。运行一天的会话可能积累数千次工具回调，每次打开页面都从第一条算起，恢复时间会随日志增长。快照保存的是“读完第几条后，状态变成了什么”。本章把快照和这条日志放进同一 SQLite 事务，只有提交之后，读端才能采用它作为起点。[SQLite 事务](https://www.sqlite.org/lang_transaction.html) · [SQLite 隔离语义](https://www.sqlite.org/isolation.html)

假设读到序号 2 时，快照记下的状态是 running，之后服务端又持久化了 paused、resumed、completed 三条事件。客户端从这份快照恢复时，只需把这三条事件按顺序交给同一个纯函数，就能算出最终的状态和票号。这个归约函数只接收旧视图和单条事件，输出新视图，既不读取本机时钟，也不持有工单服务的连接。只要输入的事件字节相同，解码后算出的视图就完全一致，且不会发起任何外部写入——这正是回放可以反复执行而不产生新工单或新审计记录的原因。[Fowler 对事件重建和外部更新的讨论](https://martinfowler.com/eaaDev/EventSourcing.html)

**Fig-23-02　从第 2 条快照重连。** 括号内为当前读端游标。即使最后一个事件先到，也只能在已验证的前缀上继续。

```text
客户端(2)       收到 5 ───── 请求 3 以后所有记录 ─── 依次应用 3、4、5 → (5)
事件服务        已持久化 1、2、3、4、5               提供已提交的连续区间
工单服务        工单已经写入                         不参与回放
```

本地实验把快照摘要保存在服务端；一旦客户端带回的快照状态被改过或已损坏，摘要比对就会失败，读端随即放弃快照，从日志开头重新回放。需要注意的是，如果保存摘要的一方本身也能改写日志，这种自算摘要只能检测意外损坏，无法防篡改。跨机器部署时还要约定一次读取的上界：本章实验先关闭写连接再以只读方式打开数据库，此时日志已经静止；在线系统则需在一致读事务中先锁定一个上界 H，只承诺把视图恢复到 H，随后再追赶新追加的记录。否则一边读一边写，“恢复完成”就没有可重复核对的基线。[LangGraph 对线程和检查点的说明](https://docs.langchain.com/oss/python/langgraph/persistence)

## 23.4 最后一条丢了

收到 5 而没收到 4，很容易发现中间有缺口。若丢的是最后一条，客户端本地看起来完全正常。它会一直显示“运行中”。实验每次重连都向权威日志读取本会话游标之后的记录，即使客户端尚未观察到跳号，这一步也要执行。传输层若能报告最后一个事件 ID，可以省去一些重复发送；应用仍需规定 ID 指向哪份历史和怎样补齐后缀。[HTML 事件流重连协议](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**Tab-23-02　同一重连入口处理的分歧。**

| 观察 | 判定依据 | 后续动作 |
| --- | --- | --- |
| 同一序号再次到达 | 权威记录在规范化后与来件相同 | 忽略已应用的记录 |
| 同一序号的内容或 ID 变了 | 与保存的事件冲突 | 拒绝该来件，从权威日志补齐 |
| 收到较大的序号 | 本地缺少连续前缀 | 保留已确认游标，从这里追赶 |
| 快照内容、会话或游标不可信 | 会话、摘要或范围校验失败 | 放弃本地快照，从日志开头恢复 |
| 老客户端仍用 seq 字段 | 已定义的 v0 迁移只改字段名及版本 | 规范化后再比较；未知版本回到可解码的权威源 |

表中的 v0 迁移只覆盖这一种已知旧格式。当服务端日志升级到读端无法解析的新版本时，读端必须停在原游标，等自身升级后再继续恢复。如果客户端直接丢弃读不懂的事件，又顺手把游标往前推了一格，界面就会在漏掉真实变更的情况下显示“已同步”。跨组件传递事件时，标明来源、标识和类型是基本约定；至于连续递增的数值序号，则是本章为了判定缺口额外引入的约束。[CloudEvents 项目](https://cloudevents.io/)

## 23.5 三种“继续”的实际结果

在仓库根目录用 Python 3.12 执行：

```shell
python examples/ch23/session_replay.py --output outputs/ch23/replay.json
```

实验用构造的教学输入调用第 36 章的工单服务，先生成三条完整会话，分别走向完成、取消和失败，其中只有完成路径实际写入了一张工单。每条会话都依次经过创建、开始、暂停、继续和终止，并在前两次转移时保存快照。随后程序关闭两个写连接，改用 SQLite 的只读 URI 重新打开数据库，对三条会话分别施加 20 种投递与快照故障条件——包括三个位置的重复、三个位置的缺失、乱序、空投递、过期或损坏的快照、旧协议版本以及错误会话身份等。原始报告记录了每次测试的实际投递序列、恢复动作、终态、工单表与审计记录表的行数以及耗时。[SQLite 只读 URI](https://www.sqlite.org/uri.html)

全部 **60/60 次**只读回放都准确恢复到了序号 5 和对应的终态：完成会话的工单数保持 1、服务审计记录保持 1，取消和失败两条会话仍为 0。单看工单数没变，还不足以证明回放过程没有触发写接口，因为第 36 章的工单服务会按操作 ID 拦截重复建单，但每次收到写请求仍会写入一条新的审计记录。因此实验同时核对了审计表行数，并只给回放程序提供事件日志的只读连接，从接口边界上杜绝了回放调用建单方法的可能。

接着以报告中的 completed 会话为基线，看最后两组写端重试对照。第一组使用原命令和**相同操作 ID**重试：服务端识别出重复键，没有新建工单，直接返回原票号 1，此时工单数仍为 1，但这次重试在服务端留下了记录，审计行数从 1 增至 2。第二组模拟只保留聊天文本的客户端，把用户点“继续”当成一次新提交，为相同载荷生成了**新操作 ID**：服务端将其视作另一笔合法申请并再次建单，工单数从 1 增至 2，审计行数从 2 增至 3。只存着聊天记录的客户端当然也可以先停下来查单，而不是直接重发；这组对照说明，单靠聊天文本本身，客户端无法拼出一个安全的重试键。有关重复请求的预期效果，可参照 [HTTP 幂等语义 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

本地报告的 elapsed_us 从开始校验快照到结束补传，用单调时钟实测，不包含网络往返、建单和生成初始日志。一次性运行这 60 个教学输入可以检验恢复逻辑；要估计服务延迟，仍需固定输入规模、引入并发负载并重复采样。[第 27 章](../part7/ch27_benchmarking_capacity.md)给出了分位数的记录方法。

## 23.6 重连验收

当用户重新打开页面时，界面可以先显示“正在核对”，等回放完成后再展示服务端确认的终态和票号。如果审批已失效但原工单早已写入，还要依据当前查询权限决定展示哪些字段：回放只负责重建状态，权限校验仍由业务服务把关。下一章把同类竞态压缩到毫秒级——界面已经进入下一轮交互，上一轮的回调却刚刚到达。[第 24 章](ch24_streaming_interrupts.md)

1. 服务端收到“取消申请”和服务端记录“申请已取消”，哪一个可以直接应用到只读视图？为什么？
2. 只剩 10 毫秒可用于恢复时，应怎样测量并调整快照间隔？
3. 游标没有跳号，界面却一直显示“运行中”。怎样区分任务真的在运行和最后一个事件丢失？
4. 工单数量没有增加，服务审计记录却多了一行，这能说明恢复流程只做了只读回放吗？它和按原操作 ID 重试有什么区别？
5. 下一轮用户输入已经开始，上一轮的完成事件才到达。哪些信息仍应写入事件日志，哪些需要在展示层过滤或核对？

**实践题。** 从报告中取出 completed 会话的 missing_middle 和 missing_end 两条记录，标出客户端最早在什么节点发现缺口，列出两条记录恢复后一致的状态字段，以及一项来自业务表的独立核对证据。随后在临时副本中去掉末尾向权威日志补传的步骤，重跑并定位第一个停在旧位置上的游标。进阶可按每 100 条、每 1000 条存一次快照，测量固定长度日志的恢复耗时，并报告实验机器配置和样本数。
