# Ch22 智能体编排与执行运行时

## 22.1 第二个用户来了

报销助手正在帮财务核对一批申请。它得读政策、取回票据，再说明哪些申请可以提交。另一个用户这时打开页面，只想看自己的申请到了哪一步。假如我们给每个请求写了一个独立的处理函数，两个人看起来应该互不影响。可把全部工具调用连到同一个执行队列之后，第二个人的第一次查询可能排在整批核对任务后面。界面还在刷新，他等来的只是自己的排队动画。

要解释这十几秒究竟花在哪里，得先把“有资格执行”和“已经得到资源”分开。计划器知道工作之间的依赖。某票据未经核对，对应的提交动作就没有资格发出。两次互不依赖的政策查询则可以同时开始，但如果下游只剩一条连接，还是得有一次等着。调度器承担这个选择，模型不应通过多生成几个工具调用来扩大配额。

本章沿这个教学场景构造一批同时到达的请求，跟踪一次短查询穿过各个等待点。读者需了解函数、异步等待和有向无环图。读完可以从运行记录区分依赖阻塞、资源等待和实际执行，并在 worker 退出后判断哪些任务可以接管。[Ch09 的任务图](../part3/ch09_task_decomposition_planning.md)给出了计划的依赖含义；这里使用其中的“任务须等前置完成”这一性质，输入是为负载实验专门构造的精简任务集。

## 22.2 一张票据的执行路径

将“核对票据”拆成两步。第一步只读，取得票据和政策；第二步使用前一步的数据整理答复。假如第一步被撤销，直接运行第二步会给用户一个没有证据的结论。实验给每个租户生成 25 个任务，前 15 个可以立即进入调度，后 10 个依赖该租户的第 0 个任务成功。两个租户的依赖各自闭合，所以一方失败时可以保住另一方的进度。

**Fig-22-01　谁持有任务，谁持有外部作用。** 本章设计图。模型和工具通过适配器接入，实验中二者均使用受控等待；真实建单边界在 Ch36。

```text
计划与依赖 → 调度器 → 租户就绪队列 → worker → 模型／工具适配器 → 外部端点
                 ↑                      │                         │
                 └── 进度、结果、失败 ←──┘                  操作 ID 与回执
                         ↓
                      状态存储
```

调度器只放行依赖已完成的任务。就绪队列保管暂时没有执行位置的工作。worker 取走一项任务后，负责用适配器调用模型或工具，并报告退出原因。适配器可以替换，调度器只关心它是否完成、超时或抛出已知错误。实验把 `lookup` 和 `format` 接到耗时可控的替身上；读者换掉其中一个函数，就能保留原来的队列和调度策略。

执行状态还要有一个地方可以查。从单机实验可导出每个任务的轨迹；进程重启后要让用户继续会话，就需要持久存储。先保存写入意图，再把操作 ID 交给工具执行器。若回执丢失，恢复者可以拿同一 ID 查询已经发生的作用。[Ch23](ch23_sessions_events_state.md)说明用户怎样从快照接着读；[Ch36](../part9/ch36_reference_implementation.md)给出了写入意图和业务工单分别持久化的实现。本章的内存调度器自身没有跨进程接管能力。

## 22.3 排在谁的后面

最朴素的调度器每次只跑一个任务。它让资源使用一目了然，代价是慢工具等待网络时，空闲的执行能力也被闲置。反过来，给全部就绪任务各建一个协程，很容易把排队搬进更难观察的地方。应用调度器说“已经开始”，但大量协程只是卡在下游连接池门口。

实验让三种实现共享一个最多五个调用同时进入的端点。串行组只有一个执行位置。无界组对就绪任务全部派发，工作量仍固定为五十项。有界组最多四个活跃 worker，每个租户最多占两个，并各用一个容量为三的就绪队列。每次派发之后把优先权交给下一个还有额度的租户。上限既限制等待中的任务数量，也决定了机器空闲时一个租户能不能借用另一个租户的位置。本实验使用硬配额，即使另一方已经收工也不借用。

**Fig-22-02　依赖图如何变成派发时序。** A、B 是两个租户；箭头表示此时允许的下一次动作，具体毫秒数见实验日志。

```text
A0 ──成功──→ A15 … A24 可进入就绪队列
B0 ──成功──→ B15 … B24 可进入就绪队列

派发      A0     B0     A1     B1       等到有 worker 退出，再补下一个位置
          └────── 这四项可重叠执行 ──────┘
控制      cancel(A0) 直接送给运行中的任务，后继留在计划中等待裁决
```

**Tab-22-01　同一批输入的资源账本。**

| 资源 | 本地配置 | 达到边界时的动作 |
| --- | --- | --- |
| 批次输入 | 两个租户，共 50 项 | 本次只接受预先枚举的有限任务；持续流量另需入口限额 |
| 就绪队列 | 有界组每租户 3 项 | 留在计划表，腾出空间后再选取 |
| 正在执行 | 全局 4，每租户 2 | 轮流派发有空位的租户 |
| 下游端点 | 共享 5 个位置 | 适配器等待信号量，在 finally 中归还 |
| 执行预算 | 正常调用 1000 毫秒 | 超时结束调用并阻塞依赖它的工作 |
| 内存 | 单批保存任务和轨迹；未测字节上限 | 长期运行时需限制输入体积和日志保留期 |

表中的执行预算从 worker 开始调用适配器算起，包含端点等待，但不含之前的排队。用户若只愿等一秒，就要在入口保存绝对截止时刻，每次派发都用剩余预算计算超时。否则一个任务可能在就绪队列等了两秒，又得到一秒完整调用时间。Python 的队列和信号量分别适用于等待容量和占用份额，两者的等待范围需在运行记录中区分。[异步队列](https://docs.python.org/3.12/library/asyncio-queue.html) · [异步同步原语](https://docs.python.org/3.12/library/asyncio-sync.html)

## 22.4 那个 worker 没有回来

考虑 A0 被取走后，其余任务陆续完成，但 A15 到 A24 一直没有进入就绪队列。盲目增加十个 worker 帮不上忙，它们都在等 A0 的成功凭据。先找 A0 最后一次派发的记录，再检查它是否产生过业务作用。对于只读检查，如果能确定旧执行已经退出，可以重新派发。对于建单，如果旧执行可能已经提交，要查操作 ID 后再决定是否重试。若无法核对，就把结果保留为未知。[AWS 关于幂等重试的工程讨论](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**Tab-22-02　执行者退出后的处理。**

| 事件 | 实验或工程中的处置 | 可见证据 |
| --- | --- | --- |
| 只读 worker 在调用端点前退出 | 本地捕获该次退出，收回份额，再次派发同一任务 | 同一任务出现两次 dispatch，依赖只在成功后放行 |
| 用户取消正在等待的任务 | 直接取消协程，回收端点与租户份额 | 取消原因及 blocked 后继；另一租户继续执行 |
| 下游调用超时 | 记录 timeout，终止依赖链 | 端点和等待者计数归零，超时与用户取消可区分 |
| 远端 worker 失联 | 设计上通过租约、接管代次、业务查账处理 | 需另外取得租约记录、写入端验证及回执；本地实验未覆盖 |

在分布式系统中，“一段时间没听见心跳”和“旧执行者已停止”是两个不同观察。旧 worker 可在新 worker 接管以后恢复网络。如果它仍能写，新旧两方就可能同时提交。租约决定此刻谁有资格工作，写入端还需要核对当前接管代次或使用业务幂等协议。即使重复写入得到控制，跨租户读取也应在服务端查权；每租户并发额度只决定资源份额。处理回执和状态协调可继续读 [Ch19](../part5/ch19_multi_agent_communication.md) 和 [Ch23](ch23_sessions_events_state.md)。

Python 中取消是协作式的。等待操作可被取消，清理代码仍需运行；调用取消以后，还要等待任务退出再声称资源已释放。实验在故障任务实际进入 worker 后安排取消，保留取消前已取得资源的清理路径。对已经发到远端的请求，一个进程的 finally 无法撤回远端事务。[Python 任务取消](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)

## 22.5 五十项任务的等待时间

从仓库根目录运行下列命令。输入配置是 YAML 的 JSON 子集，标准库可直接读取。实验每种策略运行五次，每轮轮换策略的先后。所有任务在同一批次提交；从批次开始到各任务被调度器确认完成，算作该任务的端到端延迟。慢任务至少占用端点 12 毫秒，快任务至少 3 毫秒；计时器提前唤醒时会继续等待。耗时模拟受控 I/O，未连接真实模型。

```shell
python examples/ch22/async_runtime.py --output outputs/ch22/load.json
```

**Tab-22-03　Exp-22-01 单机实测。** Windows、CPython 3.12.16。每轮五十项正常任务全部成功。下表给五轮指标的中位数；每轮总体 P95 采用 50 个任务排序后的第 48 项，交互租户首个完成时刻只取该租户最早一项。

| 策略 | 吞吐（项/秒） | 总体 P95（毫秒） | 交互租户首个完成（毫秒） | 就绪队列峰值合计 | 端点等待峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 串行 | 70.66 | 683.47 | 389.71 | 39 | 0 |
| 无界 | 437.94 | 104.11 | 50.91 | 30 | 30 |
| 有界 | 285.36 | 158.83 | 14.33 | 6 | 0 |

回答开头那个用户，最有意义的是第三列延迟指标“交互租户首个完成”。串行按租户顺序取任务，财务批次会先得到大量执行机会。无界组虽然能吃满五个端点位置，但第一批任务在端点处仍形成了等待。轮转组一开始就给交互租户派发任务，它因而最早看到结果。另一方面，有界组的最大并发主动降到了四，单租户还受两个位置约束；本批次的吞吐和总体 P95 均逊于无界组。这个比较同时改变了派发顺序与并发上限，不能把全部差异归因于轮转算法。要隔离轮转本身的影响，可以固定四个位置和相同租户配额，只替换派发顺序。

故障组让 batch-0 分别在调用前退出、进入调用时取消、在执行中超时。第一种情况下重新派发一次，最终 50 项成功。后两种情况下各有 39 项成功、1 项取消或超时、10 项因依赖失败而阻塞；交互租户的 25 项全部完成。每轮结束时端点占用和等待者均为零。读者可以从原始 trace 找到第一个 blocked 的任务，再沿 dependencies 追到 batch-0。把亮红色的十条告警合成一条根因，需要的正是这样的依赖信息。

这个批次为了可复现，让所有任务一开始就被系统接纳。计划表里暂未进队的任务也占内存，因此就绪峰值 6 并不能证明系统可接受任意长的输入流。真实部署还要定义入口拒绝策略、端点限速和过载反馈；扩 worker 之前先看等待是发生在本地还是外部服务。[Google SRE 的过载处理](https://sre.google/sre-book/handling-overload/) · [Ch27 性能与容量](../part7/ch27_benchmarking_capacity.md)

## 22.6 工单可以交给下一班了吗

交班时能说明“哪个任务已经被派过”，还不足以说明“哪一个动作已经生效”。派发与工具真实写入之间可能隔着重试、超时和回执丢失。把运行记录交给持久会话层时，应明确任务身份、尝试次数、终态以及仍需核对的业务操作。下一章从用户再次打开页面时看到的一行文字，继续追这笔申请。[Ch23 会话、事件与状态机](ch23_sessions_events_state.md)

1. 就绪队列里只有三项，而端点有三十个等待者，应从哪个观测边界解释这个差别？
2. 若把两个租户的硬配额改为闲时可借用，怎样保证另一个租户回来时仍有机会？
3. worker 退出后十个后继连续报错。怎样用事件和依赖区分一次根因与十次独立工具故障？
4. 若只公布成功任务的 P95，取消一批慢任务会怎样改变读者的判断？
5. 用户取消后工具返回一张票号，能否由调度器直接删除？需要哪些额外事实？

**实践题。** 固定同一份任务表，先把端点容量从五降为二，再保持端点容量不变、只改变 batch 的慢任务时长。分别预测等待将出现在哪一层，再用 trace、队列峰值和两个租户的 P95 核对。提交配置、原始运行报告、一条预测错误的解释，以及一次取消后资源归还的证据。进阶可实现允许闲时借用的调度器，对比首个结果与整批完成的取舍。
