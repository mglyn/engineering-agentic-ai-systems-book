# Ch22 智能体编排与执行运行时

## 22.1 第二个用户来了

报销助手正在帮财务批量核对报销申请，每条申请都要先查政策、拉取票据，再判断是否允许提交。就在这时，另一位用户打开页面，只想查一下自己的申请走到了哪一步。即使两个请求各有独立的处理函数，只要所有工具调用最终汇入同一个执行队列，后来的短查询就可能排在整批核对任务后面，页面迟迟拿不到第一条返回结果。

要弄清这段等待究竟耗在哪个环节，得先把“依赖上已经可以执行”和“已经拿到执行资源”分开。依赖关系由计划决定：票据还没核对完，对应的提交动作就不能发出。两条互不依赖的政策查询在逻辑上可以并行，但如果下游端点只剩一个空闲槽位，其中一条仍得排队。谁先拿到这个槽位由调度器裁决，模型不能靠一次多生成几个工具调用去扩大配额。

下面用一批同时到达的模拟请求还原这一场景，通过运行事件观察任务何时就绪与派发、端点等待峰值，以及故障后哪些后继被阻塞。阅读本章只需熟悉函数、异步等待和有向无环图。这里沿用了[Ch09 的任务图](../part3/ch09_task_decomposition_planning.md)中“任务须等前置完成”的依赖语义，输入则是为负载实验单独构造的精简任务集。

## 22.2 一张票据的执行路径

将“核对票据”拆成两步。第一步只读，取得票据和政策；第二步使用前一步的数据整理答复。假如第一步被撤销，直接运行第二步会给用户一个没有证据的结论。实验给每个租户生成 25 个任务，前 15 个可以立即进入调度，后 10 个依赖该租户的第 0 个任务成功。两个租户的依赖各自闭合，所以一方失败时可以保住另一方的进度。

**Fig-22-01　谁持有任务，谁持有外部作用。** 本章设计图。模型和工具通过适配器接入，实验中二者均使用受控等待；真实建单边界在 Ch36。

```text
计划与依赖 → 调度器 → 租户就绪队列 → worker → 模型／工具适配器 → 外部端点
                 ↑                      │                         │
                 └── 进度、结果、失败 ←──┘                  操作 ID 与回执
                         ↓
                      状态存储
```

调度器只放行依赖已完成的任务。就绪队列暂存已经满足依赖、但暂时领不到执行槽位的任务。worker 取走任务后，通过适配器调用模型或工具，并在结束时报告退出原因。适配器可以替换，调度器只关心调用是完成、超时还是抛出了已知错误。实验中 `lookup` 和 `format` 接在耗时可控的模拟函数上；把其中一个适配器换成真实调用，原有的队列和调度策略不用改动。

执行状态还需要有地方可查。单机实验可以直接导出每个任务的运行轨迹；但如果进程重启后还要让用户接着刚才的会话继续操作，就必须引入持久存储。做法是先落盘写入意图，再把操作 ID 交给工具执行器；一旦回执丢失，恢复流程可以凭同一操作 ID 向外部系统查证写入是否已经落地。[Ch23](ch23_sessions_events_state.md)说明用户怎样从快照接着读；[Ch36](../part9/ch36_reference_implementation.md)给出了写入意图和业务工单分别持久化的实现。本章的内存调度器自身没有跨进程接管能力。

## 22.3 排在谁的后面

最简单的调度器一次只跑一个任务。它的资源占用一目了然，代价是慢工具等待网络返回时，本地其余执行能力只能干等。反过来，给全部就绪任务直接各起一个协程，排队并不会消失，只是转移到了更难观测的下游：应用调度器记录任务“已经开始”，实际上大批协程全堵在下游连接池门口。

实验让三种调度配置共享同一个模拟端点，端点最多允许五个调用同时进入，三组运行的都是同一批五十项任务。串行组只开一个执行槽位，按租户顺序逐项执行；无界组不对本地并发设限，只要任务就绪就立即派发，由端点信号量挡住超出容量的调用；有界组把活跃 worker 总数限制为四个，每个租户最多占两个，并各配一个容量为三的就绪队列，每次派发后轮转到下一个仍有额度的租户。这里有两层约束：就绪队列容量控制排进本地队列的任务数，每租户并发上限决定执行槽位分配。本实验采用硬配额，即使一方已经全部收工，另一方也不能借用它的空余槽位。

**Fig-22-02　依赖图如何变成派发时序。** A、B 是两个租户；箭头表示此时允许的下一次动作，具体毫秒数见实验日志。

```text
A0 ──成功──→ A15 … A24 可进入就绪队列
B0 ──成功──→ B15 … B24 可进入就绪队列

派发      A0     B0     A1     B1       等到有 worker 退出，再补下一个位置
          └────── 这四项可重叠执行 ──────┘
控制      cancel(A0) 直接送给运行中的任务，后继留在计划中等待裁决
```

**Tab-22-01　同一批输入的资源账本。**

| 资源 | 本地配置 | 达到边界时的动作 |
| --- | --- | --- |
| 批次输入 | 两个租户，共 50 项 | 本次只接受预先枚举的有限任务；持续流量另需入口限额 |
| 就绪队列 | 有界组每租户 3 项 | 留在计划表，腾出空间后再选取 |
| 正在执行 | 全局 4，每租户 2 | 轮流派发有空位的租户 |
| 下游端点 | 共享 5 个位置 | 适配器等待信号量，在 finally 中归还 |
| 执行预算 | 正常调用 1000 毫秒 | 超时结束调用并阻塞依赖它的工作 |
| 内存 | 单批保存任务和轨迹；未测字节上限 | 长期运行时需限制输入体积和日志保留期 |

表中的执行预算从 worker 开始调用适配器算起，包含端点等待，但不含此前在本地排队的时间。用户如果只愿等一秒，就必须在入口记录绝对截止时刻，并在派发时按剩余时间重算超时；否则一个任务可能在就绪队列里先耗掉两秒，进入适配器后又拿到一整秒完整调用时间。Python 的异步队列适合限制缓冲排队长度，信号量适合限制并发占用槽位，运行记录里需要把这两段等待分开记账。[异步队列](https://docs.python.org/3.12/library/asyncio-queue.html) · [异步同步原语](https://docs.python.org/3.12/library/asyncio-sync.html)

## 22.4 那个 worker 没有回来

假设 A0 被取走后，其余任务陆续完成，但 A15 到 A24 始终没有进入就绪队列。这时盲目再加十个 worker 也帮不上忙，因为 A15 到 A24 都在等 A0 的成功凭据。排查应先查 A0 最后一次派发的记录，再确认它是否已经触发外部写入。如果是只读检查，只要确认旧执行已经退出，就可以重新派发；如果涉及建单，且旧执行有可能已经提交，就必须先按操作 ID 查证再决定是否重试。实在无法核对时，应把结果标记为未知。[AWS 关于幂等重试的工程讨论](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**Tab-22-02　执行者退出后的处理。**

| 事件 | 实验或工程中的处置 | 可见证据 |
| --- | --- | --- |
| 只读 worker 在调用端点前退出 | 本地捕获该次退出，收回份额，再次派发同一任务 | 同一任务出现两次 dispatch，依赖只在成功后放行 |
| 用户取消正在等待的任务 | 直接取消协程，回收端点与租户份额 | 取消原因及 blocked 后继；另一租户继续执行 |
| 下游调用超时 | 记录 timeout，终止依赖链 | 端点和等待者计数归零，超时与用户取消可区分 |
| 远端 worker 失联 | 设计上通过租约、接管代次、业务查账处理 | 需另外取得租约记录、写入端验证及回执；本地实验未覆盖 |

在分布式系统中，“一段时间没收到心跳”和“旧执行者已经停止”是两回事。旧 worker 完全可能在新 worker 接管后恢复网络；如果它还能继续写，新旧两方就会同时提交。租约用来约束此刻谁有资格执行，但写入端仍须核对当前的接管代次或依赖业务幂等协议。另外，每租户并发额度只负责隔离资源份额，不能替代权限校验；即便重复写入已经受控，跨租户读取依然必须在服务端查权。回执处理与状态协调可继续读 [Ch19](../part5/ch19_multi_agent_communication.md) 和 [Ch23](ch23_sessions_events_state.md)。

Python 中的任务取消是协作式的。等待操作可以被取消，但清理代码仍要跑完；发出取消请求之后，必须等到任务真正退出，才能把资源计为已释放。实验等到故障任务实际进入 worker 之后再触发取消，借此检验任务在退出前是否把已占用的资源释放干净。对已经发往远端的请求，本地进程的 finally 块无法撤回远端事务。[Python 任务取消](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)

## 22.5 五十项任务的等待时间

从仓库根目录运行下列命令。输入配置是 YAML 的 JSON 子集，标准库可直接读取。实验每种策略运行五次，每轮轮换策略的先后。所有任务在同一批次提交；从批次开始到各任务被调度器确认完成，算作该任务的端到端延迟。慢任务至少占用端点 12 毫秒，快任务至少 3 毫秒；计时器提前唤醒时会继续等待。耗时模拟受控 I/O，未连接真实模型。

```shell
python examples/ch22/async_runtime.py --output outputs/ch22/load.json
```

| 策略 | 吞吐（项/秒） | 总体 P95（毫秒） | 交互租户首个完成（毫秒） | 就绪队列峰值合计 | 端点等待峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 串行 | 70.66 | 683.47 | 389.71 | 39 | 0 |
| 无界 | 437.94 | 104.11 | 50.91 | 30 | 30 |
| 有界 | 285.36 | 158.83 | 14.33 | 6 | 0 |

回到开头交互用户的等待问题，单看“交互租户首个完成”就能看出策略间的取舍：有界组将这一指标从无界组的 50.91 毫秒压到了 14.33 毫秒，代价是整体吞吐和总体 P95 均弱于无界组。需要注意的是，三组配置同时改变了派发顺序、总并发上限、每租户配额和就绪队列设置，因此观察结果反映的是整套配置的综合表现，不能单独归因于其中某一项。若要隔离单一因素的作用，必须控制其余变量不变，例如固定总并发为 4、每租户配额为 2 且队列容量一致，只替换派发顺序，或固定派发顺序而单独调整总并发与租户配额。

故障组让 batch-0 分别在调用端点前退出、进入调用时取消、以及在执行中超时。第一种情况下，调度器收回份额并重新派发一次，最终 50 项全部成功；后两种情况下各有 39 项成功、1 项取消或超时、10 项因前置依赖失败而阻塞，交互租户的 25 项全部完成。每轮结束时，端点占用数和等待者计数均归零。排查时可以从原始 trace 找到第一个 blocked 的任务，再沿 dependencies 一路追到 batch-0；把十条连续报错归并成同一条根因，靠的就是这条依赖信息。

这个批次为了可复现，让所有任务一开始就被系统接纳。计划表里暂未进队的任务也占内存，因此就绪峰值 6 并不能证明系统可接受任意长的输入流。真实部署还要定义入口拒绝策略、端点限速和过载反馈；扩 worker 之前先看等待是发生在本地还是外部服务。[Google SRE 的过载处理](https://sre.google/sre-book/handling-overload/) · [Ch27 性能与容量](../part7/ch27_benchmarking_capacity.md)

## 22.6 向持久会话层交接的边界

把执行记录交给持久会话层时，只记下“哪个任务已经被派发过”，还不足以说明“哪一个外部动作已经生效”。派发记录和工具真实写入之间，可能隔着重试、超时和回执丢失。交接数据里必须明确任务身份、尝试次数、终态以及仍需查证的业务操作。下一章接着追踪这笔申请在页面重新打开后的状态恢复与事件回放。[Ch23 会话、事件与状态机](ch23_sessions_events_state.md)

1. 就绪队列里只有三项，而下游端点却积压了三十个等待者，应从哪个观测边界解释这个差别？
2. 若把两个租户的硬配额改为闲时可借用，怎样保证另一个租户回来时仍有机会？
3. batch-0 取消或超时后，十个后继被标记为 blocked。怎样用事件和依赖区分一次上游根因与十次独立故障？
4. 若只公布成功任务的 P95，取消一批慢任务会怎样改变读者的判断？
5. 用户取消后工具返回一张票号，能否由调度器直接删除？需要哪些额外事实？

**实践题。** 固定同一份任务表，先把端点容量从五降为二，再保持端点容量不变、只改变 batch 的慢任务时长。分别预测等待将出现在哪一层，再用 trace、队列峰值和两个租户的 P95 核对。提交配置、原始运行报告、预测与实测的对照说明（含偏差原因或关键判断依据），以及一次取消后资源归还的证据。进阶可实现允许闲时借用的调度器，对比交互租户首项完成时间与整批完成时间的取舍。
