# 第六篇：运行时工程与交互基础设施

财务人员批量核对申请时，另一个用户发来一笔报销。系统为这个用户分到执行位置，查完政策，开始建单。用户关闭页面，又从手机重新连上。他听到助手正在播报旧金额，便打断它，换上一张新票据，说“照右边这个改”。一个任务从排队走到这里，至少要保住四件事：任务能得到执行、工单提交记录能找回、旧输出及时停住、新输入指向正确的对象。

| 读到这里 | 手里已有的输入 | 交给下一步的证据 |
| --- | --- | --- |
| [Ch22 智能体编排与执行运行时](ch22_orchestration_runtime.md) | 带前置依赖的任务和两个租户的执行预算 | 派发、完成、取消或依赖失败的逐任务轨迹 |
| [Ch23 会话、事件与状态机](ch23_sessions_events_state.md) | 已确认的业务事实、原操作 ID、客户端游标 | 可恢复的视图，以及可以核对的原工单 |
| [Ch24 流式流水线、流量控制与用户打断](ch24_streaming_interrupts.md) | 会话、轮次和生成代次 | 旧片段最后一次呈现、生产者退出和新一轮首段输出 |
| [Ch25 多模态交互与实时协调](ch25_multimodal_realtime.md) | 带来源和时间的语音、图像及文件引用 | 有版本依据的对象关联，或要求用户澄清的理由 |

**篇末实践。** 选择一笔提交后失去回执的申请。为它设计一次“断线、重连、停止播报、换图改金额”的交互。先画出两条时间线，分别表示用户看到的内容和服务持久化的业务事实；再对每一次恢复或打断指出可沿用的身份、必须变化的身份和独立验收途径。评分时分别核查工单数、旧片段数和新票据引用；三个事实都能从运行证据中找到，才足以解释这次交互。基础实验入口见各章；各章共享术语和接口登记见[附录 C](../appendix_c_schemas.md)。
