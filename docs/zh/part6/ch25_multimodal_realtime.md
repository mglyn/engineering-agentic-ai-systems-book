# Ch25 多模态交互与实时协调

## 25.1 右边是哪张票

用户刚把界面切到新版页面，指着屏幕说：“帮我核对右边这张停车票。”他面前的页面已经刷新，系统返回的却是上一页旧票据的编号。听录音或核对已标注的转写，原话明确指的就是右边的停车票；要定位偏差，得把用户看到的页面与服务端收到的页面按时间并排比对。

在本章的 late_frame 右侧用例（receipt-03）里，源端在第 1000 毫秒采集页面版本 2，用例将指向词的时间标注构造在 1190 毫秒（并非对 WAV 测得的词级识别时间）。随后语音定稿于 1250 毫秒送达协调器，页面版本 2 却延迟至 1360 毫秒才到达。在这 110 毫秒的空档里，协调器缓存中仍只有旧版画面，便按“取最新已到帧”的规则去定位“右边”——每一步都正常通过，结果却落在了上一版页面上。

**Fig-25-01　同一次指向在两个观察点上的时间线。** 数值来自本章 late_frame 用例的模拟时钟，单位为毫秒。采集时刻和接收时刻只在各自标出的观察点有意义。

```text
页面与输入端   1000 拍下 page@2 ─── 1190 用户指向它的右侧对象
协调器         400 收到 page@1 ───────── 1250 收到定稿 ── 1360 收到 page@2
立即决策                                  取旧图右侧对象
等待引用版本                              保留请求 ──────── 取新图右侧对象
```

[上一章](ch24_streaming_interrupts.md)在输出侧给文本和音频片段加上生成代次，防止上一轮回答继续往外播。转到输入侧，系统要解决另一半问题：用户这一轮说的“右边这张”，到底指哪一版画面里的哪个对象。本章实验不运行语音识别或图像识别模型，转写文本与页面事件都已预先标注好，同时保留原始票据图和录音，方便核对实际音频长度与图中标签。把识别结果固定下来以后，就可以只打乱传输顺序，观察关联判定是否跟着改变。

## 25.2 给“这个”留下出处

语音事件里的 page@2 并非麦克风听出的版本号，而是本例在构造输入时预先绑定了页面版本与指向时点。若推广到允许用户边说边换页的真实 UI，一种可选设计是同时记录视图更新时间与指向词所在的时间区间，借此对齐两者；一旦无法确定用户指向哪一版页面，就直接请用户确认，而不要拿随后拍到的画面去回猜先前所指的对象。

**Tab-25-01　从输入设备交给协调器的最小信息。** 可执行样例的字段源见 `examples/ch25/multimodal_event_schema.json`。

| 字段 | 本例中的值或含义 | 解释错误会怎样 |
| --- | --- | --- |
| session_id、turn_id、event_id | 会话、当前输入轮次、该片段的唯一标识 | 另一轮迟到的定稿会抢占解释权 |
| captured_ms、received_ms | 源端记录的发生时间、协调器本地接收时刻 | 网络迟到会被误读成用户刚换图 |
| kind、payload.ref | 语音、画面或文件；所指页面及版本 | 即使时间靠近，也可能拿到另一份文件 |
| revision、final、speaker | 转写版本、定稿标志、发言者来源 | 半句和旁人的补充可能被直接当成指令 |
| objects、side | 此版本页面左右两处的稳定对象 ID、所指方向 | 左右布局相同，背后的票号仍可能已更换 |

“捕获时刻更近”和“指的是同一对象”分别是时间条件与语义条件。两帧画面可能几乎同时拍下，却来自不同用户的窗口；同一份带版本的文件即便晚到，依然可能是那次指向对应的证据。本章的保守规则还要求，采纳的图像不能早于用户指向时刻 300 毫秒以上——这是一个可调的教学阈值。静态文件如果有可靠的不可变文档标识，可以单独放宽有效期；快速滚动的摄像画面则要收得更紧。

文件、传感器和手势也可加入同一条证据链。文件需带页码、内容版本和区域，才知道“右边”是原图右侧还是裁剪预览的右侧。指针事件带坐标，但缩放或平移后的坐标还需通过当时的视图变换还原。传感器要保留设备来源、单位、采样时间和有效期，例如旋转方向影响左右映射时，应选取显示该画面时的姿态。当前执行样例实际读取图片和文件事件；姿态与指针是协议扩展设计。[W3C Pointer Events](https://www.w3.org/TR/pointerevents3/) · [Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)

## 25.3 什么时候可以答复

串行语音链可以先等端点检测判定一句话说完，再取最终转写、关联图片、生成文本、合成语音。这样方便留存各步输入，却把全部等待都推到了用户说完之后。实时链则可以在用户讲话期间先准备好画面对象，按增量转写实时显示字幕并预取相关政策。预取是只读操作，猜错了直接丢弃即可；但把“左”听成“右”的临时结果——哪怕只存在 80 毫秒——一旦触发工单修改，就会留下真实的副作用。哪些步骤能提前做，取决于错误预测能否安全作废。[LiveKit 的轮次与打断机制](https://docs.livekit.io/agents/logic/turns/)

在本地样例里，初稿和定稿分别标为 revision 1 和 2。revised_transcript 用例会先送来一条方向相反的初稿，两种对照实现都会等到定稿再选择对象，用来充当基线对照。如果连这一组也失败，应该先排查是否把临时字幕当成了正式业务输入，而不是急着去调网络等待参数。

**Fig-25-02　从收集证据到产生一条回复。** 每次解释保留所用轮次和页面版本，以便用户核对。

```text
收集输入 ── 临时转写 ─→ 更新候选，仍在收集
    │
  用户定稿 ── 发言者冲突 ─→ 请用户确认说话人
    │
  查目标版本 ── 缺失 ─→ 等待迟到素材 ── 到限 ─→ 请用户补图或报编号
    │                         │
    └────────── 找到同轮同版且有效的对象 ─→ 展示核对结果
```

端点检测通常只能估计用户是否已经说完。一次短停顿可能只是换气，背景里的另一个人也可能接着说“左边”。本章遇到发言者仍有歧义时，把两种候选留给用户澄清。若某一协议允许在定稿之后继续修订，就还需要显式撤销旧定稿，并决定哪些下游步骤可以重开。给一个词打上 final 标志，无法替执行器撤回已经批准的写入。

当轮次 T 的答复仍在播放，T+1 已开始说话时，输出侧依靠上一章的代次检查，输入侧另存 T+1 的来源和视图版本。两者独立演进。把它们都塞进一个可随时覆盖的“当前帧”变量，旧的识别回调就会读到刚更新的画面，生成一个事后看似自洽、当时却不存在的组合。

## 25.4 等待的代价

为了让 late_frame 用例得到正确答案，协调器在收到定稿后等待目标素材，教学上限是 200 毫秒。这一等待并非总能换来答案。after_deadline 的图在 1700 毫秒才到，比 1450 毫秒的截止点晚。继续等会延迟用户纠正输入的机会，直接选旧图则会给出错误票号。此处应明确告知用户缺哪份材料，并允许用带编号的文本继续。

**Tab-25-02　证据缺失时显示给用户什么。**

| 触发条件 | 用户可见行为 | 恢复条件 |
| --- | --- | --- |
| 当前轮图片晚到 | 暂存指向，界面显示正在读取当前票据 | 截止前收到匹配版本且时间有效的素材 |
| 图片未到，已上传同版文件 | 从文件版本解析对应对象，展示编号供核对 | 文件引用、轮次、对象映射均一致 |
| 画面过期或等到截止 | 请求重新展示，或让用户直接输入票号 | 收到新的明确输入，另记决策 |
| 两人重叠、归属不清 | 说明听到了两个方向，请当前用户确认 | 确认发言者和对象，避免代用户提交 |
| 无麦克风或用户关闭采集 | 保留文本和文件通道 | 用户明确启用音频后重新建立时间映射 |

把“稍微等一等”放到输出侧，要解决的是另一件事。字幕和声音对应同一段内容时间，但音频包与字幕包经过网络时延迟各不相同，哪个先到就立刻播，用户直接面对的就是忽快忽慢的音画错位。常见做法是给两条流定一个共同的计划呈现时刻：早到的包先在缓冲里等到时间再输出，晚到的则记一次超时；实际接收端还得规定超过多久就直接丢包，免得缓冲越积越长。另外，RTP 里不同媒体的时钟频率和起点往往不同，直接把原始时间戳相减没有意义，必须先换算到同一个时间基准上。[RFC 3550 §5.1、§6.4.1](https://www.rfc-editor.org/rfc/rfc3550) · [WebVTT 的媒体时间与 cue](https://www.w3.org/TR/webvtt1/)

隐私约束也会改变故障排查的方式。线上可以保留输入引用、版本、决策记录和时差数据，原始音视频则另按用途、授权和保留期限管理。用户关闭摄像头后，后续输入应明确标成“画面不可用”。如果一直沿用上一次缓存的旧画面，系统表面上还能继续作答，用户却很难察觉它看的早已不是眼前的内容。

## 25.5 把到达顺序打乱

实验提供 20 组原创票据图和合成中文短语音。每张 SVG 里有左右两张卡片，各自带编号；同名 WAV 朗读与该用例指向相符的句子。你可以先打开 receipt-03 的图片，听一遍同名录音里的“帮我核对右边这张停车票。”，对照左右卡片写下预期编号，再核对用例记录里的 expected。脚本会读取实际音频长度和图中的标签，但本身不运行语音识别，关联计算直接使用预先标注好的转写与页面事件。这样既能拿原始素材核对结果，也能在没有语音模型的机器上复现整组实验。

```shell
python examples/ch25/media_sync.py --output outputs/ch25/media.json
python examples/ch25/playout.py --output outputs/ch25/playout.json
```

十种到达情形各做两个方向，一共 20 组。两策略共享输入。到达策略在第一条定稿到达时选最近收到的素材；约束策略先核轮次和发言者，再核页面引用和发生时间，等不到则请用户澄清。总判定把“该选中目标时选对”和“证据不足时请求澄清”都计为正确，下面再拆开看分母。

| Exp-25-01，按业务预期分组 | 到达策略 | 约束策略 |
| --- | ---: | ---: |
| 证据足够，选对对象（含文件后备） | 4 / 12 | 12 / 12 |
| 证据不足或发言者冲突，正确请求澄清 | 0 / 8 | 8 / 8 |
| 两组合计 | 4 / 20 | 20 / 20 |

在转写修订用例中，两种方法都返回正确编号。在旧轮定稿迟到的两例中，到达策略把上一轮的话应用到这一轮的画面，记录甚至显示捕获差为负。若把所有输入都按接收时间排成一条线，这个错误很容易被误读为“响应速度快”。约束策略在两个文件后备用例中各等 80 毫秒，在两个迟到画面用例中各等 110 毫秒；永远缺图、图像过期或超出截止的六例各等满 200 毫秒。两例发言者冲突在当前用户定稿时直接转澄清。这些都是从合成时间线算出的等待，读者可以改等待预算观察答案何时变化。

第二条命令把每段 WAV 的时长分成六个对齐点，构造音频与字幕两条接收轨迹。每种缓冲方案共有 120 个点。以“字幕呈现时刻减去音频呈现时刻”定义带符号偏差，比较其绝对值；不设缓冲时最大绝对偏差为 **110 毫秒**，共用 **80 毫秒**缓冲后为 **40 毫秒**。代价同样能从日志读出：所有用例中，首段音频最早开始的时间从 10 毫秒移到 80 毫秒。这是虚拟播放时钟实验，真实扬声器和显示器上的同步误差需要另布探针。[高精度时间规范](https://www.w3.org/TR/hr-time-3/)

## 25.6 报出票号再继续

用户指着画面说“右边”时，只要证据齐全，就可以把关联到的票号直接展示出来供核对；即便错过了等待窗口，回一句“我没有收到您刚换的图，请报一下票号”，任务照样能往下走。涉及金额修改时，这两种做法都比默默沿用旧图更容易核验。真正提交修改时，仍要按新的请求参数和审批条件单独校验，不能把一次正确的对象关联直接当成写入授权。

1. 图片和声音相差只有 5 毫秒，但属于不同轮次，哪项证据能阻止错误关联？
2. 字幕初稿写“左边”，定稿改为“右边”。哪些预取结果可以保留，哪些动作必须推迟？
3. 用户关闭摄像头后系统仍可回答票据细节。怎样区分来自用户上传文件的证据和过期画面？
4. 如果只有八个应澄清的用例，直接统计“给出票号的比例”会怎样影响方案选择？
5. 用户打断旧播报并换图。输入的页面版本、输出的生成代次、工单的操作 ID 各在哪一步核对？

**实践题。** 选取 late_frame、after_deadline 和 file_fallback 三个用例，先用纸笔推演：把等待预算从 200 毫秒降到 100 毫秒后，哪一项结果会改变。再运行脚本，对比修改前后的输入与决策时间线、选中对象编号以及澄清次数，并说明为什么语义关联全部正确，仍然不足以证明音频与字幕同步。进阶任务可改用自己录制且经参与者同意的素材，用真实的采集和播放时钟复测其中一项指标，并记录误差范围与原始素材的删除安排。
