# Ch39 部署演练、持续交付与工程综合实践

## 39.1 旧版本回来了，谁还能批工单？

值班同学面对两条互相矛盾的消息。发布脚本说旧版本已经启动；刚刚撤销审批权的只读观察员，却仍被程序识别为可以审批。昨天留下的那张 250 元申请还在库里。此刻如果开放入口，团队究竟恢复了什么？

这是本书构造的预发布事故。上一章检验了候选的决策、工具行为和轨迹。那份报告在一组确定的输入上仍然有效。进入下一环境以后，程序同时读取现场的政策配置、角色清单和权限缓存；三者的组合在构建时还没有出现。我们沿用 PRJ-3 的申请，让带版本号的检查程序实际读取这些状态。观察员权限只用于本例的权限判定，全程通过只读连接查单。学生可以观察到错误授权决定，同时保留未被修改的业务现场。[Ch38 回归门禁](ch38_regression_fault_injection.md)

读完本章，你应该能在发布前说出哪张工单可以用来验收，在失败时留下足够的信息判断影响面，并让接班人亲自验证回滚。交接时最有用的问题往往很具体：换回旧程序以后，观察员还被授予哪些动作？原工单的操作身份、载荷与审批摘要还匹配吗？

## 39.2 同一张申请经过三个环境

申请号是 T-DEMO-01。第 36 章在服务端提交后中止第一次运行，第二个进程接着处理，保留一张工单和一条创建事件。这个时间窗口很适合做发布练习：数据库已经承担了对用户的承诺。把它删掉再演示一次，出现一张外表相同的新工单，也会丢失我们需要验证的连续性。[Ch36 参考实现](ch36_reference_implementation.md)

**Fig-39-02　教学部署拓扑与信任边界。** 下图中的箭头是本机进程调用或文件读取。两种发布制品都用 Python 启动。

```text
作者修改合成输入 → 第36章引擎 → PRJ-3 工单库、事件库
测试进程 → 独立的临时数据库 → 第37章测试、第38章切片报告
发布驱动 → r1.pyz 或 r2.pyz → 只读查询同一份 PRJ-3 工单库
                          ↘ 政策配置、角色清单、外置权限缓存
接班人 ← release.json ← 每阶段的版本、进程状态和五项业务核对
```

本地档允许作者改一条合成输入并观察控制流。测试档从仓库的固定输入开始，各测试在各自目录运行；观察员无需共用开发者机器上的旧会话。教学预发布档把检查程序打成独立的 pyz 制品，在新进程里运行，每个阶段读取同一份 PRJ-3 工单库。两版制品故意只改变修订标识，保持检查逻辑一致，把实验变量集中在环境与回滚次序上。三个档位均采用标准输入输出或子进程调用，不配置外部网络端点和凭据。配置表见 `examples/ch39/deploy/profiles.json`。

把这个拓扑映射到团队环境时，需要重新回答几个问题。容器镜像由谁构建、按什么摘要拉取？发布身份能否修改运行身份？哪个组件可以读取秘密值，哪类日志会越过团队边界？配置是进程启动时的快照，还是运行时会刷新？例如把 ConfigMap 作为环境变量注入容器后，修改对象不会让运行中的进程自动获得新值。同一版本的两个进程因此可能读到不同政策。课堂把配置放在文件里、每阶段起新进程，限定了观察发生的时点。[Kubernetes ConfigMap](https://kubernetes.io/docs/concepts/configuration/configmap/)

这里的代码摘要只能标识相同字节。课堂驱动同时负责构建和核查，无法用自己生成的摘要给自己签发组织信任。团队实际放行时，构建者、部署者、业务批准者的身份来自不同可信渠道。审批引用某一制品、环境与证据包，批准后重新构建的制品需要重新核对。[Ch30 生产治理](../part7/ch30_production_governance.md)

## 39.3 把发布决定写成能失败的流水线

先记录打算交付什么。驱动从同一份源码生成两个带修订号的归档，记录 SHA-256，然后调用第 36 章的三项目复现、运行第 37 章行为测试，并重新执行第 38 章十二个回归切片。每一步接收实际的子进程结果。构建失败、测试进程异常会中断执行；有意模拟测试漏跑或日志含合成标记时，驱动留下 hold 报告并以非零状态结束。前一种情况下接班人要保留失败进程的输出，可能还没有最终 JSON。

**Fig-39-01　从提交到预发布演练。**

```text
检出源码 → 构建带摘要的制品 → 三项目复现 → 行为测试 → 回归切片
                                                        ↓
归档 ← 恢复验收 ← 注入环境错配 ← 受控部署 ← 合成日志标记检查
  ↓
具名人员审阅业务事实、环境差异与例外 → 记录批准或退回
```

**Tab-39-01　发布就绪检查。**

| 门槛 | 本地证据 | 不满足时的决定 |
| --- | --- | --- |
| 使用指定解释器和可识别制品 | 第 36 章环境记录、两个归档摘要 | 重新按锁定环境构建 |
| 三项目能复现 | 每个项目的状态、PRJ-3 两轮退出记录 | 在失败项目上重现 |
| 指定行为测试已执行 | pytest 子进程成功和摘要 | 漏跑即 hold |
| 回归材料对应本次运行 | 同一输出目录的 gate.json、十二行结果 | 回到首个分歧切片 |
| 构建日志没有预置的合成秘密标记 | 日志文件和扫描决定 | 停止并定位写日志的位置 |
| 业务状态及权限正确 | 五项独立字段与观察值 | 冻结扩大发布并核对 |
| 实际上线授权 | 组织批准者、环境、范围、有效期 | 人工审阅保持待办 |

为什么保留一个明知会被拦下的日志？因为只跑干净日志，扫描器即使从不读取文件也能交出同样结果。练习把一个完全公开的教学字符串写进构建日志，再要求驱动真的读取这个文件并停止发布。这个实验只能发现指定标记。真实系统还要审阅字段白名单、依赖与权限、日志受众和秘密轮换；课堂里没有这些真实秘密，也没有组织批准者。[Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/) · [GitHub 部署环境与审批](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

## 39.4 在什么时点可以宣布恢复？

先看五次进程能否正常返回。如果仪表板只显示这个信号，从第一行到最后一行都会是绿灯。再打开业务观察值。第三行的进程读到了错误政策，观察员的权威权限和缓存权限都包含 approve。第四行已经换回旧程序，配置和权威清单都正确，剩下的差异居然只在缓存里。这个区别决定了值班人的下一步动作。

**Fig-39-03　一次运行的因果次序。** 横向是事件次序，每个位置对应报告的一行，不代表等长的墙钟时间。

```text
稳定 r1 → 受控发布 r2 → 注入错配 r2 → 回退制品并还原配置、角色 r1 → 失效缓存再读 r1
 通过         通过          暂缓                   暂缓                         通过
```

**Tab-39-02　怎样知道回退真的生效。**

| 对象 | 事故中采取的动作 | 恢复时独立核对 |
| --- | --- | --- |
| 代码 | 用上一版归档启动新进程 | 实际修订号与制品摘要 |
| 配置 | 还原政策版本及通信档位 | 新进程读到的配置与预期相等 |
| 数据 | 保留已有工单库并只读查询 | 租户、操作 ID、完整载荷、批准摘要、一条创建事件 |
| 权限 | 收回观察员的 approve | 权威角色清单只含 read |
| 缓存 | 失效旧条目并让新进程重读 | 生效权限只含 read |

回滚过程要给数据留一条单独的路。这里两个版本均能读同一数据库格式，故可以在原库验证。真实业务在发布窗口可能已经接受新的合法请求，整库恢复旧快照会抹掉这些写入。遇到不兼容迁移时，应先限制写入，列出已接受的操作，演练兼容读或向前修复，分别验证新旧记录；本次课堂运行没有进行库表迁移。[SQLite 只读 URI](https://www.sqlite.org/uri.html) · [Kubernetes Deployment 修订与回滚](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

有一条告警在恢复后才出现。练习把第三阶段的失败观察延迟送到第五阶段后，留下采样阶段与到达阶段。对历史事故它是准确的，对“此刻仍有故障”的判断却已经过期。值班人重新拉取当前业务探针，保留历史失败，并在报告中写明何时取得恢复证据。更复杂的环境还需要区分不同实例的流量份额和采样窗口；本例对照来自同机依次启动的进程。[Google SRE 金丝雀发布](https://sre.google/workbook/canarying-releases/) · [Kubernetes 健康探针](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)

## 39.5 亲手交付这次演练

在仓库根目录使用已安装项目测试依赖的 Python 3.12。给每次演练取一个新目录名，防止新尝试覆盖上次事故现场。以下命令可以使用普通 CPU，不下载模型。PRJ-3 的模型响应与时间来自第 36 章确定性夹具。

```shell
python examples/ch39/ci/drill.py --output outputs/ch39/release-01
python examples/ch39/ci/drill.py --output outputs/ch39/missing-01 --fault skip-tests
python examples/ch39/ci/drill.py --output outputs/ch39/log-01 --fault log-marker
```

第一条应输出 drill-passed 并退出 0。这表示演练观察到了预定的失败，也验证了恢复。打开 release.json，核对五个阶段的 process_healthy、accepted 和 facts。第二、三条都应输出 hold 并退出 1。分别检查 gates.tests 与 gates.log_marker_absent；两份报告的 timeline 应当都是空的。若运行期间解释器报错，要检查标准错误与执行阶段，不能把“任意非零退出”算作门禁命中。

综合练习包含三个小项目。PRJ-1 的基础任务是从原始申请追到一张合法工单，进阶任务是改写一个不满足政策的输入并说明拒绝发生在哪里。PRJ-2 的基础任务是核对协调结果与最终工单，进阶任务是比较一个参与者缺席时哪些断言仍可验证。PRJ-3 的基础任务是在进程中断后复用原操作身份，进阶任务是把恢复后的业务库交给五阶段演练，并解释每个红灯对应的实际状态。每种变体都要单列输入、预期与结果，变体结果不能冒充本章归档数据。[Ch34 综合项目](../part8/ch34_capstone_reference_architectures.md) · [Ch37 行为测试](ch37_agent_testing.md)

把演练搬到多人共享的预发布服务，还要交代流量如何隔离、谁能执行回退、是否有足够样本观测候选、正式凭据由谁注入。固定响应可以反复命中同一事故位置；真实模型对语义、提示与工具选择的影响属于另一组实验，需要登记模型、数据、抽样次数与失败分布。第 39 章没有据此测量模型质量、并发容量或真实生产恢复时间。

再把上一章的缺陷客户端真正送进同一个发布入口。它在成功建单后多发一次相同操作，仍会返回原工单。发布人在这个环节能不能看到上一章已经定位的八个差异？

```shell
python examples/ch39/ci/drill.py --output outputs/ch39/client-01 --fault client-regression
```

应输出 hold，退出 1。打开 release.json，gates.regression 为假，timeline 为空，说明流程在切换预发布制品前停止。regression_evidence 保留发生失败的八个切片、实际子进程退出码、候选配置摘要，以及同目录 gate.json 的文件摘要。按这个引用打开报告，可以直接从 ordinary 切片的重放审计开始调查。若文件缺失或子进程本身没有产出报告，需按执行异常处理；空报告不能解释为业务断言成功或失败。两次放行演练即使使用相同的制品，携带的回归证据也需逐次核对。

## 39.6 接班人拿到什么

交接包位于 `examples/ch39/`。release_checklist.md 说明发布前查什么，rollback_runbook.md 说明事故后按什么顺序查，release_report.md 对照已运行的四种结果，final_capstone_rubric.md 供教师或另一组同学验收。原始记录保留机器决定和人工审阅状态。另一位同学可以在干净检出中重新运行，核对逻辑结果，记录环境差异并撰写自己的审阅意见。[附录 C 接口](../appendix_c_schemas.md) · [附录 D 部署](../appendix_d_deployment.md) · [附录 F 安全](../appendix_f_security.md)

1. 一次演练里，为什么所有进程都能正常返回，业务仍会连续失败两次？
2. 怎样证明回滚后读到的还是之前获批的那张申请？只看工单总数会漏掉哪些变化？
3. 一个观察员的权威角色已经恢复，但权限探针仍包含 approve。接下来要保留哪条证据，动哪个组件？
4. 同一条告警在故障时与恢复后到达，值班人应分别在什么证据上做决定？
5. 第 38 章回归通过，这次预发布也通过。把其中哪项批准交给自动脚本会越过本实验的授权边界？

**实践题。** 提交一次正常演练和三次阻断演练的报告。在客户端回归这一组，按 release.json 的摘要核对 gate.json，再指出第一处多发的调用。选择第四阶段，说明只看进程状态的同学会做出什么决定，你依据哪个观察值要求暂停。由另一人从新目录重跑，记录人工判定、允许的范围与尚未覆盖的生产条件。评分项见综合项目量规。
