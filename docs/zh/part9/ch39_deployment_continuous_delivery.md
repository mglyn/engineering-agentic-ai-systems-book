# Ch39 部署演练、持续交付与工程综合实践

## 39.1 旧版本已启动，权限探针仍报 approve

在演练的第四阶段，旧版程序已经重新启动，权威角色清单里只读观察员也只有 read 权限，但新进程读取的外置权限缓存仍含 approve，只读探针因此报告权限尚未恢复。其间只读观察员并未实际操作审批，本地工单库里的 250 元旧工单则留作后续验收。只要外置缓存中的旧条目尚未失效，仅凭进程启动成功还不能放开入口。

这是本书构造的预发布事故。上一章在固定输入集上检验了候选版本的决策、工具行为与轨迹，那份报告在该输入集上依然有效。进入预发布环境后，程序还要同时读取现场的政策配置、权威角色清单和外置权限缓存，这三者的运行时组合在构建阶段尚未出现。本章沿用 PRJ-3 的申请，让带修订号的检查程序读取这些现场状态；实验全程通过只读连接查单，并以只读探针观察观察员实际生效的权限，并未真的由观察员执行审批，从而在复现错误权限判定的同时保留未被修改的业务现场。[Ch38 回归门禁](ch38_regression_fault_injection.md)

完成本轮演练后，交接记录需要落到四项可核查的事实：发布前指定用于验收的工单、失败时用来界定影响面的现场状态、换回旧程序后探针读到的观察员生效权限，以及原工单的操作身份、载荷与审批摘要的核对结果。

## 39.2 同一张申请经过三个环境

申请号是 T-DEMO-01。第 36 章在服务端提交后中止第一次运行，第二个进程接着处理，保留一张工单和一条创建事件。这个时间窗口很适合做发布练习：数据库已经承担了对用户的承诺。把它删掉再演示一次，出现一张外表相同的新工单，也会丢失我们需要验证的连续性。[Ch36 参考实现](ch36_reference_implementation.md)

**Fig-39-02　教学部署拓扑与信任边界。** 下图中的箭头是本机进程调用或文件读取。两种发布制品都用 Python 启动。

```text
作者修改合成输入 → 第36章引擎 → PRJ-3 工单库、事件库
测试进程 → 独立的临时数据库 → 第37章测试、第38章切片报告
发布驱动 → r1.pyz 或 r2.pyz → 只读查询同一份 PRJ-3 工单库
                          ↘ 政策配置、角色清单、外置权限缓存
接班人 ← release.json ← 每阶段的版本、进程状态和五项业务核对
```

本地档允许作者修改单条合成输入并跟踪控制流。测试档从仓库的固定输入起步，各测试在独立临时目录中运行，互不干扰，也不会复用开发者本机残留的旧会话状态。教学预发布档将检查程序打包成独立的 pyz 制品并在新进程里运行，每个阶段只读查询同一份 PRJ-3 工单库。两版制品特意只改动修订标识而保持检查逻辑一致，把实验变量限定在环境配置与回滚次序上。三个档位均使用标准输入输出或子进程调用，不配置外部网络端点和凭据，配置表见 `examples/ch39/deploy/profiles.json`。

把这套拓扑映射到团队环境时，需要逐项明确运行边界：容器镜像由哪条流水线构建、按哪份摘要拉取；发布身份是否拥有修改运行身份的权限；哪些组件可以读取敏感凭据，哪类日志会流出团队边界；配置是在进程启动时固化为快照，还是在运行期间动态刷新。例如把 ConfigMap 作为环境变量注入容器后，修改对象不会自动更新已运行进程的环境，同一版本的两个进程因此可能读到不同政策。本实验将配置写入文件并在每阶段启动新进程，从而固定每次观测读取配置的时点。[Kubernetes ConfigMap](https://kubernetes.io/docs/concepts/configuration/configmap/)

这里的代码摘要只能标识相同字节。课堂驱动同时负责构建和核查，无法用自己生成的摘要给自己签发组织信任。团队实际放行时，构建者、部署者、业务批准者的身份来自不同可信渠道。审批引用某一制品、环境与证据包，批准后重新构建的制品需要重新核对。[Ch30 生产治理](../part7/ch30_production_governance.md)

## 39.3 把发布决定写成能失败的流水线

流水线先锁定待交付的对象。发布驱动从同一份源码打包出两个带修订号的归档并记录 SHA-256，随后依次调用第 36 章的三项目复现、运行第 37 章行为测试，并重新执行第 38 章的十二个回归切片，每一步都依据子进程的真实返回结果推进。构建失败或测试进程异常会立即中断执行，此时可能尚未生成最终 JSON，接班人需要保留失败进程的标准输出与错误日志；若是演练刻意注入的测试漏跑或日志含合成标记，驱动则会写入 hold 报告并以非零状态退出。

**Fig-39-01　从提交到预发布演练。**

```text
检出源码 → 构建带摘要的制品 → 三项目复现 → 行为测试 → 回归切片
                                                        ↓
归档 ← 恢复验收 ← 注入环境错配 ← 受控部署 ← 合成日志标记检查
  ↓
具名人员审阅业务事实、环境差异与例外 → 记录批准或退回
```

**Tab-39-01　发布就绪检查。**

| 门槛 | 本地证据 | 不满足时的决定 |
| --- | --- | --- |
| 使用指定解释器和可识别制品 | 第 36 章环境记录、两个归档摘要 | 重新按锁定环境构建 |
| 三项目能复现 | 每个项目的状态、PRJ-3 两轮退出记录 | 在失败项目上重现 |
| 指定行为测试已执行 | pytest 子进程成功和摘要 | 漏跑即 hold |
| 回归材料对应本次运行 | 同一输出目录的 gate.json、十二行结果 | 回到首个分歧切片 |
| 构建日志没有预置的合成秘密标记 | 日志文件和扫描决定 | 停止并定位写日志的位置 |
| 业务状态及权限正确 | 五项独立字段与观察值 | 冻结扩大发布并核对 |
| 实际上线授权 | 组织批准者、环境、范围、有效期 | 人工审阅保持待办 |

演练专门保留了一份必然触发拦截的构建日志。如果只测试干净日志，哪怕扫描器根本没有读取文件，也会返回同样的通过结果。这里把一段完全公开的合成标记字符串写入构建日志，要求驱动实际读取该文件并阻断发布。这项检查只能命中预置标记；真实系统还需审阅字段白名单、依赖与权限范围、日志受众以及凭据轮换，而本实验既不包含真实凭据，也不包含组织级批准者。[Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/) · [GitHub 部署环境与审批](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

## 39.4 五阶段业务恢复验收

五个阶段的进程全部正常退出。如果监控面板只显示进程存活，从第一行到最后一行都会亮绿灯。核对只读业务探针的观察值后，异常才会浮现：第三阶段的新进程读到了错误政策，观察员在权威角色清单和权限缓存中的条目都包含 approve；第四阶段已经换回旧版制品，政策配置与权威角色清单也已还原，但新进程读到的外置权限缓存里仍留着 approve。正是这个差异决定了值班人的下一步动作——不是继续回退代码，而是清理旧缓存条目并重新采样。

**Fig-39-03　一次运行的因果次序。** 横向是事件次序，每个位置对应报告的一行，不代表等长的墙钟时间。

```text
稳定 r1 → 受控发布 r2 → 注入错配 r2 → 回退制品并还原配置、角色 r1 → 失效缓存再读 r1
 通过         通过          暂缓                   暂缓                         通过
```

**Tab-39-02　怎样知道回退真的生效。**

| 对象 | 事故中采取的动作 | 恢复时独立核对 |
| --- | --- | --- |
| 代码 | 用上一版归档启动新进程 | 实际修订号与制品摘要 |
| 配置 | 还原政策版本及通信档位 | 新进程读到的配置与预期相等 |
| 数据 | 保留已有工单库并只读查询 | 租户、操作 ID、完整载荷、批准摘要、一条创建事件 |
| 权限 | 收回观察员的 approve | 权威角色清单只含 read |
| 缓存 | 失效旧条目并让新进程重读 | 生效权限只含 read |

回滚过程要给数据留一条单独的路。这里两个版本均能读同一数据库格式，故可以在原库验证。真实业务在发布窗口可能已经接受新的合法请求，整库恢复旧快照会抹掉这些写入。遇到不兼容迁移时，应先限制写入，列出已接受的操作，演练兼容读或向前修复，分别验证新旧记录；本次课堂运行没有进行库表迁移。[SQLite 只读 URI](https://www.sqlite.org/uri.html) · [Kubernetes Deployment 修订与回滚](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

脚本没有运行长驻服务，也不会在恢复后再在线重采，而是把第三阶段的失败采样作为迟到告警，与第五阶段已取得的恢复观察并列写入报告，并同时记录采样阶段与到达阶段。在真实现场遇到类似迟到告警时，值班人应保留这条历史记录，并按采样时间判断是否需要复查：采样早于已确认的恢复时点时，它只反映此前的故障，不必据此推翻恢复结论；若采样晚于恢复时点或当前缺少恢复后的观测证据，才需要重新采集只读业务探针。更复杂的生产环境还需区分不同实例的流量份额与采样窗口，而本章的所有对照均来自同机依次启动的进程。[Google SRE 金丝雀发布](https://sre.google/workbook/canarying-releases/) · [Kubernetes 健康探针](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)

## 39.5 运行发布与阻断演练

在仓库根目录使用已安装项目测试依赖的 Python 3.12。给每次演练取一个新目录名，防止新尝试覆盖上次事故现场。以下命令可以使用普通 CPU，不下载模型。PRJ-3 的模型响应与时间来自第 36 章确定性夹具。

```shell
python examples/ch39/ci/drill.py --output outputs/ch39/release-01
python examples/ch39/ci/drill.py --output outputs/ch39/missing-01 --fault skip-tests
python examples/ch39/ci/drill.py --output outputs/ch39/log-01 --fault log-marker
```

第一条应输出 drill-passed 并退出 0。这表示演练观察到了预定的失败，也验证了恢复。打开 release.json，核对五个阶段的 process_healthy、accepted 和 facts。第二、三条都应输出 hold 并退出 1。分别检查 gates.tests 与 gates.log_marker_absent；两份报告的 timeline 应当都是空的。若运行期间解释器报错，要检查标准错误与执行阶段，不能把“任意非零退出”算作门禁命中。

综合练习包含三个小项目。PRJ-1 的基础任务是从原始申请追到一张合法工单，进阶任务是改写一个不满足政策的输入并说明拒绝发生在哪里。PRJ-2 的基础任务是核对协调结果与最终工单，进阶任务是比较一个参与者缺席时哪些断言仍可验证。PRJ-3 的基础任务是在进程中断后复用原操作身份，进阶任务是把恢复后的业务库交给五阶段演练，并解释每个红灯对应的实际状态。每种变体都要单列输入、预期与结果，变体结果不能冒充本章归档数据。[Ch34 综合项目](../part8/ch34_capstone_reference_architectures.md) · [Ch37 行为测试](ch37_agent_testing.md)

若将这套演练迁到多人共享的预发布服务，还需明确流量如何隔离、谁有权执行回退、样本量是否足以观测候选版本表现，以及正式凭据由谁注入。固定响应适合反复复现同一事故位置；真实模型在语义理解、提示敏感度与工具选择上的表现属于另一组实验，需要单独登记模型、数据、抽样次数与失败分布。第 39 章没有据此测量模型质量、并发容量或真实生产环境的恢复时间。

接下来将上一章的缺陷客户端送入同一个发布入口。它在建单成功后会多发一次相同操作，虽然仍返回原工单，但行为轨迹已经偏离预期。执行以下命令，核对发布门禁能否直接暴露上一章已经定位的八个差异：

```shell
python examples/ch39/ci/drill.py --output outputs/ch39/client-01 --fault client-regression
```

应输出 hold，退出 1。打开 release.json，gates.regression 为假，timeline 为空，说明流程在切换预发布制品前停止。regression_evidence 保留发生失败的八个切片、实际子进程退出码、候选配置摘要，以及同目录 gate.json 的文件摘要。按这个引用打开报告，可以直接从 ordinary 切片的重放审计开始调查。若文件缺失或子进程本身没有产出报告，需按执行异常处理；空报告不能解释为业务断言成功或失败。两次放行演练即使使用相同的制品，携带的回归证据也需逐次核对。

## 39.6 接班人拿到什么

交接包位于 `examples/ch39/`。release_checklist.md 说明发布前核查清单，rollback_runbook.md 说明事故后的排查顺序，release_report.md 对照已运行的四种结果，final_capstone_rubric.md 供教师或另一组同学验收。原始记录同时保留程序的自动判定与人工审阅状态。接手人可在全新检出的工作区中重新运行，核对逻辑结果，记录环境差异并补写自己的审阅意见。[附录 C 接口](../appendix_c_schemas.md) · [附录 D 部署](../appendix_d_deployment.md) · [附录 F 安全](../appendix_f_security.md)

1. 一次演练里，为什么所有进程都能正常返回，业务核对仍会连续失败两次？
2. 怎样证明回滚后读到的还是之前获批的那张申请？只看工单总数会漏掉哪些变化？
3. 当观察员的权威角色清单已经恢复，只读权限探针返回的生效权限仍包含 approve 时，接下来应先保留哪条证据，再处理哪个组件？
4. 同一条告警分别在故障期间与恢复完成后到达，值班人应各以哪些证据作为判定依据？
5. 第 38 章回归通过，这次预发布也通过。把其中哪项批准交给自动脚本会越过本实验的授权边界？

**实践题。** 提交一次正常演练和三次阻断演练的报告。在客户端回归这一组，按 release.json 的摘要核对 gate.json，再指出第一处多发的调用。针对第四阶段，说明只看进程存活状态会做出什么判断，以及你依据哪项探针观察值要求暂停放行。由另一人从新目录重跑，记录人工判定、允许的范围与尚未覆盖的生产条件。评分项见综合项目量规。
