# Ch38 评估回归、故障注入与可观测测试

## 38.1 两个绿色的完成提示

在各自隔离的本地数据库中，对同一笔金额 250 元、申请身份相同的报销单分别运行两种客户端的恢复流程，两边最终都显示“已完成”。可分别检查两个库中的工单记录，前一个库里建出了两张工单，后一个库里只留下一张。这是[第 37 章](ch37_agent_testing.md)构造的受控缺陷：有缺陷的客户端在重试时换用了新的操作 ID，服务端据此执行了两次有效创建；修复后的客户端沿用原操作 ID，在中断后先核对服务端是否已经建单，避免重复创建。

重新运行这对客户端，如果只看最终回复，两次都会通过。改用独立的 SQLite 连接统计工单表和创建审计事件，缺陷客户端的结果是 2 和 2，修复客户端是 1 和 1。保留这个能稳定复现的坏版本有个实在的用处：以后有人打算精简验收脚本，拿坏版本再跑一遍，马上就能看出检查是不是弱化到连已知缺陷都拦不住了。

现在团队准备发布第三个版本，改动可能小到只是从提示里删去一句“请列出政策依据”。单靠一次交互顺利完成，没法判断这次改动能不能放行。我们需要把业务期望独立保存在待测版本之外，选出可能受影响的关键任务切片，用完全相同的输入分别跑基线版和候选版，把放行或暂缓决定落到具体的工单记录、执行轨迹和版本摘要上。本章样例运行在参考环境 Python 3.12 下，仓库根目录里的所有命令都不需要网络或密钥。

## 38.2 一笔普通申请掩盖了什么

第 36 章的教学政策规定，金额 250 且手续齐全的境内申请可以在既有授权下创建工单。金额换成 350，就越过了需要主管审批的界限。本地助手不能代办这个审批，应当告知用户下一步找谁。两条任务的差别只有一个数字，验收条件却完全不同。把它们合成一个“答得对不对”的平均分，会让高频普通申请支配结论。[第 26 章](../part7/ch26_evaluation_methods.md)给出了按风险切片报告的理由。

实验在 golden_slices.yaml 单独登记十二个切片。每项预先写清会话终态、允许创建的工单数量，以及适用时的原因码。主管审批切片要求 rejected、零工单、needs_approval；普通切片要求 completed 且只有一个正确载荷的工单。控制程序另外读取服务端保存的授权摘要，检查它与实际载荷相符。期望来自任务与政策语义，候选程序不能用自己的输出倒推本次标准。

**Fig-38-01　从修改到发布决定。** 本图为本章本地门禁的执行路径。

```text
固定任务、政策和输入摘要
      ├─ 基线配置 ──→ 独立数据库 ──→ 业务事实、轨迹、原因
      └─ 候选配置 ──→ 独立数据库 ──→ 业务事实、轨迹、原因
                    同一切片配对比较
                           ↓
                 有必需断言失败 → hold
                 全部通过       → pass → Ch39 读取
```

本实验的判定门槛很明确：一笔申请在授权范围内最多只能写入一张工单，缺少授权时必须为零；只要少了任何一条必需的因果记录，就直接暂缓发布。这类硬性断言不适合套用“允许上下浮动 5%”的宽容度。如果换成评估真实模型的摘要质量，就需要另行登记重复次数、随机波动和人工可接受的差异，通过抽样来做回归核查；容量与延迟则应沿用[第 27 章](../part7/ch27_benchmarking_capacity.md)的负载条件和分位数。本章的一次脚本化运行能验证控制路径是否按规则生效，不能用来估算线上的真实拒绝率。[Anthropic 对任务轨迹与实际结果的区分](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 38.3 拒绝了，原因却变了

把模型替身从 fixed-v1 切换到 fixed-v2。这个受控替换只改变主管审批切片的提案，将 needs_approval 错报为 eligible。执行器重新计算政策，发现提案与政策相冲突，保护了写入边界，因而没有建单。若验收程序只检查“有没有生成违规工单”，两个版本都会亮绿灯。可对用户来说，恢复路径已经变了：旧版能明确指向主管审批，新版得到的是一个提案错误。

**Fig-38-02　supervisor 的第一处分歧。** 来自 model-change 的实际对照。两条轨迹的事件名称完全相同，区别藏在拒绝原因里。

```text
基线    session_created → proposal_accepted → rejected(needs_approval)
候选    session_created → proposal_accepted → rejected(proposal_not_supported)
数据库                   两条路径均为 0 张工单
```

再看 after_commit 切片。服务已经写单，客户端没有来得及保存回执便触发中断钩子。测试关掉两个库连接，重新打开，继续原来的请求。此时可接受的路径包括查询原操作和核对后置条件。连续执行和恢复执行的轨迹长度会不同，要求所有事件逐字相等会错杀正常版本。反过来，只找一条 completed 又太弱。我们的断言要求 intent_saved、action_requested、postcondition_verified、completed 按这个次序出现，并单独检查服务端的创建次数。

**Fig-38-03　把断言放在能观察到事实的地方。**

```text
提案／审批        → 意图持久化      → 服务端事务         → 状态完成
检查决定和原因      检查租户与操作键   独立读工单及授权摘要   检查终态与事件次序
                                               ↘ 重开存储后再次核验
```

实验保存的是单任务本地事件日志。每条记录包含租户、任务、序号、类型和详情，样例中的一个数据库只处理一条申请，所以能检查序号连续。跨服务排查时，可以沿 trace ID 和父子 span 找到具体调用；采样、重试或导出延迟都可能造成观测缺口，业务表仍有独立价值。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/) · [W3C Trace Context](https://www.w3.org/TR/trace-context/)

## 38.4 在哪一步拔掉连接

主动注入故障来检验断言之前，先定好两条边界。第一条是隔离范围：每个任务各用独立的临时目录、两份 SQLite 数据库和受控时钟。第二条是停止条件：每个切片最多调用两次引擎，两轮后仍查不清结果，就停在 pending 状态并让门禁报错。这样即便某个切片超时，也不会波及其他任务，更不会向真实企业系统重复提交。[故障实验的稳态假设与影响范围](https://principlesofchaos.org/)

**Tab-38-01　Exp-38-01 的九个故障切片。** 原始报告保存各次引擎返回、适配器调用和实际事件。所有注入均在本地教学边界。

| 注入位置 | 应当看见的保护 | 解除故障后的验收 |
| --- | --- | --- |
| 回查接口首次超时 | outcome_unknown，保留原意图 | 下一次调用按原键查询，最终一张单 |
| 创建后回执丢失 | response_unknown | 同次调用补查得到票号 |
| 服务提交后客户端中断 | 中间状态 interrupted | 重开连接，出现 outcome_resolved，计数仍为一 |
| 本地创建额度首次耗尽 | 适配器发出可重试超时，保留尝试记录 | 额度恢复后按预算创建一次 |
| 首次结果核验返回否 | verification_pending | 重新核验原票据，不重复创建 |
| 授权在提交前到期 | action_rejected，原因 approval_expired | 无工单；这笔请求不能继续写 |
| 政策配置版本错配 | 拒绝并记录 policy_version | 无工具写入；需纠正配置再开新任务 |
| 已写单后收到取消 | cancelled_outcome_checked | 会话取消，仍查到一张真实存在的本地工单 |
| 轨迹导出丢失结束事件 | 首份导出缺少必需事件 | 从存储重新导出，事件补齐，工单数量不变 |

表里最后两行最容易把断言写反。取消只是会话的终态，工单则是先前事务已经落库的写入结果；如果硬性规定“只要状态为 cancelled 就必须零工单”，反倒会把正确的实现判错。轨迹导出丢行正好相反：工单和会话状态本身都正常，只是导出的记录不全，当前拿不到验收依据。实验会先拿这份残缺轨迹跑一遍断言并记下失败项，再从已提交的本地日志重新导出，只有完整记录才允许走业务放行。当然，如果源日志本身就已经缺失，重新导出也补不回来。[第 24 章](../part6/ch24_streaming_interrupts.md)对照说明了同一份回执在界面与账本里的不同用途。

## 38.5 把差异报告交给发布人

从仓库根目录运行以下命令。第一条必须退出 0，第二条在这个已知的缺陷候选上应退出 1，并写出报告。第三条用于比较两个已有结果；它的顺利结束表示差异报告生成成功，发布决定仍读取 decision 字段。

```shell
python examples/ch38/regression_runner/run.py --output outputs/ch38/base.json
python examples/ch38/regression_runner/run.py --candidate model-change --output outputs/ch38/model.json
python examples/ch38/regression_runner/compare.py outputs/ch38/base.json outputs/ch38/model.json --output outputs/ch38/diff.json
```

**Tab-38-02　相同十二个切片上的五次运行。** 每组一次，基线和候选使用相同输入文件。各组失败数不能相加当作不同缺陷的总数。

| 配置 | 唯一改变的输入 | 未通过切片 | 决定与首要调查方向 |
| --- | --- | ---: | --- |
| baseline | 无 | 0 / 12 | pass；保留原始报告 |
| model-change | 固定模型响应在主管切片改变决定 | 1 / 12 | hold；检查该切片的提案与原因 |
| prompt-change | 脚本化提示只要求引用第一条政策 | 11 / 12 | hold；检查提案引用是否齐全 |
| config-change | 绝对截止从 5000 改为 900，逻辑时钟起点为 1000 | 10 / 12 | hold；查 deadline_reached |
| client-change | 客户端在成功回执后再发一次相同写请求 | 8 / 12 | hold；查工具调用和服务端重放审计 |

提示变更只让 11/12 而非全部切片失败，是因为 wrong_policy 切片在核对政策版本时就按预期拒绝了任务，根本没走到后面的引用检查。配置变更也是同理，只失败了 10/12 而非 12/12：该实验将绝对截止时间设为 900、逻辑时钟起点设为 1000，但代码在回查发现无原工单、准备发出创建请求前才检查截止时间，主管审批与政策版本错配在此之前就已拒绝，不受截止时间影响。把这些仍然通过的切片和失败切片放在一起看，能更快划出改动实际波及的范围。需要明确的是，这里的 prompt-change 和前面的模型响应一样都是受控替身，适配器按脚本把提示选项直接映射为引用字段，实验并未测量真实语言模型在自然语言提示下的随机波动。

如果发布时确需放行例外，报告里必须写清批准人、适用切片、到期时间和重跑条件。本地基线的 exceptions 为空，十二个切片全部为必过项。门禁拦截后，发布人先按报告定位首个分歧：模型提案和提示问题转给适配器维护者，政策与授权问题转给业务维护者，事件残缺则转给运行时维护者。如果两份报告的输入摘要不一致，比较脚本会直接拒绝比对；修订测试集必须留下修改原因和批准记录，不能为了一次发布悄悄改掉预期结果。

### 收到成功回执后的冗余重发

普通切片的基线只向工具发三次请求：查原操作、创建工单、核验结果。现在把客户端换成缺陷版本：它在收到成功回执后，又用完全相同的操作 ID 再提交了一次。服务端把第二次请求识别为幂等重放，直接返回原票号，并没有多建工单。结果用户看到的仍是完成，数据库里依然只有一张工单，引擎记录的业务事件类型和顺序也完全没变。如果只看终态、工单数和事件顺序这三项常规指标，这个退化版本就会直接通过。

```shell
python examples/ch38/regression_runner/run.py --candidate client-change --output outputs/ch38/client.json
python examples/ch38/regression_runner/compare.py outputs/ch38/base.json outputs/ch38/client.json --output outputs/ch38/diff-client.json
```

| ordinary 切片的观察位置 | 已放行基线 | 出错的客户端 |
| --- | --- | --- |
| 申请终态、服务端创建数 | completed，1 | completed，1 |
| 工具边界记录 | lookup → create → verify | lookup → create → create → verify |
| 服务端对已创建操作的重放审计数 | 0 | 1 |
| 发布门禁 | 通过 | 暂缓；调用序列与重放数都偏离约定 |

服务端虽然靠幂等保护挡住了重复建单，门禁仍然必须阻断这次发布。这十二个切片在运行前就定好了规则：只有在返回不明时才按原操作 ID 查账，**已明确收到成功回执后不应再次发送创建请求**。多余的写请求会白耗工具配额；换到不保证同键幂等的下游服务，后果还会从浪费配额演变成重复建单。本实验只核对并统计了调用序列与服务端重放次数，额外费用和非幂等服务的实际损失并未实测。第 23 章允许断线后用原键重试，处理的是结果尚未确定的恢复场景；这里客户端已经拿到成功回执，两处判断的分界线在于发送方当时掌握的证据不同。[第 23 章会话恢复](../part6/ch23_sessions_events_state.md)

不过，门禁也不能把出现两次 create 一律判错。rate_limited 切片第一次发送在适配器内遇到配额拒绝，并没有在服务端落库，预登记的合法序列本来就包含两次 create，且两次之间必须先查账。no_grant 切片同样会调用一次创建接口，但会在服务端授权边界被拦下，业务创建数必须为零。**尝试调用、成功提交和已提交操作的重放，是三件分别计数的事。** 各切片因此既要记录客户端的调用序列，又要通过只读连接核对服务端的提交与重放审计。[第 29 章安全边界](../part7/ch29_security_safety_alignment.md)

在 client-change 候选跑完的十二个切片里，有八个走到了成功创建路径，这八个全部被调用序列与重放审计两项检查拦下；其余四个在产生成功回执前就已结束。每条失败记录都会保留 old_calls、new_calls 以及基线和候选各自的重放数。排查时直接把问题单转给客户端维护者，附上 ordinary 切片的四次调用序列、同一张票的创建与重放审计记录，并注明修复约束：去掉成功回执后的冗余重发，但必须保留失败后的查账恢复逻辑。如果图省事只从服务端删掉重放审计，只会让这类退化更难定位。

## 38.6 发布前留下什么

[第 39 章](ch39_deployment_continuous_delivery.md)承接的输入是一份包含候选配置摘要、源码与测试输入摘要、各切片原始事实、失败原因和最终决定的报告。发布模板里只写一句“回归通过”，还原不了多建工单或冗余重发的现场。把已知的坏客户端和这份能让它报错的报告一并留档，下次调整门禁脚本本身时，就有了现成的对照基线。

1. 两个客户端都返回 completed，要排查重复建单，最先应当通过独立连接查询哪两项记录？
2. 主管审批切片已经拦住了违规建单，为什么门禁仍应暂缓该候选版本？
3. 两次运行的最终回复相同但事件数不同，哪类差异可以放行，哪类必须追查原因？
4. 如果把“已写单后收到取消”这一切片的验收标准改成“零工单”，会误导团队怎样修改实现？
5. 基线任务被删掉一条，结果变成十一项全部通过。发布方应当核查哪些输入摘要与切片总数？

**实践题。** 依次运行基线、模型候选和配置候选，挑出一个终态相同但原因不同的切片，以及一个创建次数发生变化的切片，整理出输入摘要、首个分歧、独立业务计数以及给维护者的修复建议；随后恢复原配置重跑，在新报告中核对这两组结果。进阶练习可接入真实模型，对同一批任务重复抽样，并补充报告模型输出波动、调用费用、抽样范围和阻断阈值。
